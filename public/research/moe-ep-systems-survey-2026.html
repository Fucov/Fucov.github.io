01 · EXECUTIVE SUMMARY

不是再写一个负载均衡器，而是重新理解 EP 的真实执行成本

2026 年的研究进展已明显越过“按 Token 数均衡”：专业化路由使专家热点真实存在；临时复制既能减少 Straggler 又需要搬权重；固定的 GEMM Tile 与 HBM Streaming 使均衡后的 Token 数并不对应最短运行时间；低延迟协议和 Megakernel 又会重新改变调度成本。

本报告主张：当下最有研究潜力的不是单独的 EPLB、A2A Kernel 或 Expert GEMM，而是它们的共同 Critical Path：不同 Batch/Prefill/Decode、网络拓扑和运行时动态条件下，如何在不引入额外阻塞的前提下选择 Replica Placement、Token Assignment、Communication Protocol 与 GEMM Execution。

这是研究假设，尚不能宣称为“未被任何文献覆盖的空白”。TEMPO、OverlapAdvisor、MegaFlux、CascadeEP、Relief 已分别覆盖其中的一部分；可发表性取决于对它们做清晰、可验证的差分贡献。

重要阅读原则：各篇论文的“× 倍”具有不同 Baseline（No Balancing、Static EPLB、DeepEP、Fixed Placement、不同 GEMM）。不能将所有最佳加速比排列成排名，更不能把 Kernel Latency 等同于 End-to-End Throughput。未经论文明确声明的局限，会标为“研究判断”。
02 · TAXONOMY

MoE 的五个独立优化决策

① Placement / minutes

哪些逻辑专家在哪些 GPU 驻留？Replica Budget 和 HBM 怎么分？基线 EPLB；CRAFT、Sem-MoE。

② Predict & Replicate / layers

提前预测下层热点，把权重传输隐藏到上一层？Libra、PROBE、MegaFlux。

③ Dispatch / batch or step

给定当前 Router Output，每个 Expert 的 Token 派到哪个副本？LPLB、TEMPO、Relief。

④ Protocol & Kernel / µs

用什么缓冲区、同步协议、Grouped GEMM、MegaMoE？DeepEP、NVLinkOneSided、DA-MoE。

⑤ Readiness & Pipeline / request

Attention-Prefill 各 Replica 不同步到达时，何时让 Expert 开工？CascadeEP。

⑥ Topology & Scaling

单 NVLink Domain 与跨节点 RDMA 的延迟、带宽、拥塞和故障恢复差异。UltraEP、TEMPO、SGLang Roadmap。

同一层 MoE 的关键路径

Router / Top-K

Token → 逻辑 Expert；保留 Routing 语义。

Physical Routing

逻辑 Expert → 实体 Replica；跨设备分配。

Dispatch → GEMM

数据移动、等待、Weight Streaming、Tile Padding。

Combine

汇聚结果并恢复 Token 顺序；同步进入下一层。

一种更准确的调度目标是以最终关键路径为准：

TMoE = critical_path(Tdispatch, Tweight_move, Tgrouped_GEMM, Tcombine, Tplanning, Toverlap)
这是本报告的抽象，不是某篇论文原始公式。Overlapping 的执行阶段不能简单相加；具体依赖图必须取自真实实现。

Prefill / Decode 的研究对象不同

PrefillDecode
Token 形态常见较大 N，Grouped GEMM 计算/排队更明显每步活动 Token 较少，固定 Launch/通信/同步开销占比高
核心矛盾Attention 完成不同步，Streaming FFN、权重复制能否隐藏Per-step 负载瞬变，100µs 决策过贵，GEMM 小 Shape 效率低
代表路径CascadeEP、Libra、UltraEP、MegaFluxRelief、TEMPO、NVLinkOneSided、DA-MoE
注意事项Compute 与 Communication 可重叠程度依赖 Batch/Token 数不能把高吞吐 Prefill 结论直接迁移到 Decode

DeepEP / EPLB / LPLB

DeepSeek Expert Parallel Communication and Load Balancing Stack
原文 / 正式发表 ↗ 代码 / Artifact ↗
前几位作者 / 通讯DeepSeek-AI（团队署名；库内贡献者信息应以各项目记录为准）
署名机构DeepSeek
实验室/研究线索DeepSeek Infra
建立 Prefill 吞吐优先与 Decode 低延迟的通信基线；EPLB 管理较慢速率的专家副本放置，LPLB 在每个 Batch 对已有副本分配 Token。

不同 GPU 拥有不同专家，Router 输出后必须 Dispatch/Combine；热点专家会拖慢同步的整个 EP Group。

将专家副本放置（slow timescale）、Token 分配（batch timescale）与通信协议（kernel timescale）拆开；不同层次能独立优化，也会互相制约。

DeepEP 设计高吞吐/低延迟路径及相应通信布局；EPLB 按负载进行专家放置/冗余；LPLB 使用 LP 最小化 Rank Token 数最大值，单 SM 求解器利用 cuSolverDx/cuBLASDx。

DeepSeek 的项目 README 提供 API、测试脚本与实现；SGLang 2026.06 的 Waterfill/LPLB 工程文章报道在所测配置下的吞吐增益。不是一篇单独同行评议论文。

官方 LPLB README 明确：只按 Token 数平衡，未纳入 Grouped GEMM 非线性耗时；intra-node solver 约 100µs，跨节点更久；极端全局失衡可能不如 EPLB。

成为所有新调度研究的最小基线：至少量测静态 EPLB、Waterfill/LPLB 与完整 DeepEP Critical Path。

CRAFT

Fine-Grained Cost-Aware Expert Replication for Efficient Mixture-of-Experts Serving
原文 / 正式发表 ↗ 代码 / Artifact ↗
前几位作者 / 通讯Adrian Zhao, Zhenkun Cai, Zhenyu Song, Lingfan Yu；通信作者 Adrian Zhao
署名机构Amazon；University of Toronto
实验室/研究线索Amazon × UofT 联合研究；以专家放置/容量预算为主
副本数并不是越多越好；重复复制的边际收益下降，还会吞掉 HBM。

如何在总显存预算有限时，对不同层配置最有价值的冗余专家，而不浪费内存？

不同层、不同专家的负载分布与复制收益不一样；应优化复制的边际收益，而不是用统一复制率。

对各层 Replica Benefit 估计；在容量约束下通过动态规划分配副本预算，再做容量感知放置；提供面向工作负载漂移的再配置。

论文在百亿到万亿参数 MoE 相关测试里，相对既有复制方法平均端到端吞吐 1.14×、最高 1.20×；有 MLSys Artifact 和核心实现。

研究判断：主要优化偏慢时间尺度的副本数/位置；对每 Step 的 Token 分配、Copy/Transfer 的关键路径和运行时非线性 kernel 费用需要其他工作补足。论文未将这些说成统一的显式局限。

与 TEMPO（快速 Dispatch）及 UltraEP（动态副本）形成明显双层优化线索。

Semantic Parallelism / Sem-MoE

Redefining Efficient MoE Inference via Model–Data Co-Scheduling
原文 / 正式发表 ↗
前几位作者 / 通讯Yan Li, Zhenyu Zhang, Zhengang Wang, Pengfei Chen, Pengfei Zheng；原文标注 Yan Li 与 Zhenyu Zhang 共同一作，Pengfei Zheng 为通讯作者
署名机构Huawei Technologies；Sun Yat-sen University
实验室/研究线索华为 × 中山大学联合研究；独立于其他团队的机构谱系
专家放置和 Request/Token Device Scheduling 单独优化会导致无谓跨卡传输。

假设 Token 对专家的激活具有稳定统计偏好，怎样从数据入口开始减少远程 Expert Dispatch？

真正可以优化的是 Expert 与会访问它的 Token 的共置关系，而不仅是让各 GPU 平均负载相等。

离线按专家协同激活做聚类放置；Attention-DP 时在请求级选择 Device；Attention-TP 时在请求内对 Token 重排；整套 Sem-MoE 集成 SGLang。

ICLR 2026 正式论文报告全链路远程流量减少与吞吐提升；具体跨模型数字请查原文实验图，不把论文各条件下的最好值直接横比。

研究判断：依赖可预测的激活关联；输入分布变化、极端热点、请求前缀局部性以及在线迁移代价可能侵蚀收益，必须重新做实验。

与训练方向 PlaceMoE（2026.10）出现‘共同优化 Expert Layout 和数据位置’的独立呼应。

未核实独立公开仓库；论文说明已在 SGLang 实现

Libra

Effective yet Efficient Load Balancing for Large-Scale MoE Inference
原文 / 正式发表 ↗ 代码 / Artifact ↗
前几位作者 / 通讯Jaehoon Yang, Yushin Kim, Seokwon Moon, Yeonhong Park, Jae W. Lee
署名机构Seoul National University（SNU-ARC 代码与作者研究线索）
实验室/研究线索SNU Architecture Research Center，持续研究系统与硬件协同
预测下一层 Expert 热点，在权重传输还没阻塞下一层时进行动态复制。

单纯动态 Replica Planning 会引入拷贝与调度成本；如何保证这些成本不抵消负载均衡收益？

相邻层 hidden state 存在足够的变化连续性，可以提前预测下一层 Router；重构 Local/Remote 执行次序可以创造隐藏通信的时间窗。

Gate-based Lookahead Predictor；局部优先 Expert Replica Placement；CPU Cython Token Sharding；本地 Expert 先计算，远端传输和热专家复制与之重叠。

8×H200 上两个大型 MoE 模型，Prefill 吞吐最高 +19.2%；官方仓库给出 SGLang v0.4.10 复现实验路径与依赖。

仓库明确运行需要 8×Hopper NVLink 环境、部分实验极大 RAM/日志数据；研究判断：预测质量、专家副本预算和模型软件版本会影响迁移性。

与 PROBE 的跨层预测、MegaFlux 的权重管线是一条‘提前计算控制决策’的方法谱系，但机构与作者不同。

PROBE

Co-Balancing Computation and Communication in MoE Inference via Real-Time Predictive Prefetching
原文 / 正式发表 ↗
前几位作者 / 通讯Qianchao Zhu, Xucheng Ye, Yuliang Liu, Haodong Ouyang, Chengru Song
署名机构Kling Infra / Kuaishou Technology（论文署名）
实验室/研究线索快手/KlingAI 的动态专家调度研究线
工作负载偏斜不仅使某 GPU 计算拖尾，还会使 Dispatch 网络发生拥塞，即论文所称 double penalty。

在 Continuous Batching 和热点突变下，怎样提前调度专家复制，同时不和当前 MoE All-to-All 抢带宽？

决策需要提前做、Copy 需要分阶段做；算力/网络两端的平衡必须一致。

Gate-initialized Online Lookahead；Hardware-aware Balance Planner；Phase-locked Co-Scheduling 将专家权重传输隐藏在恰当的计算窗口，避免与 All-to-All 竞争。

作者报告 Prefill Latency 最高 1.32×、Decode 吞吐最高 1.26× 的改善，效果与热点波动有关。

研究判断：预测误差、可隐藏窗口不足、通信拥塞和复制成本决定失效区间；这些是依据模型推演，不能冒充论文作者明确的 Future Work。

与 TEMPO 共享作者 Chengru Song；同一研究机构围绕运行时成本与路径决策形成互补问题。

LLEP

Least-Loaded Expert Parallelism: Load Balancing an Imbalanced Mixture-of-Experts
原文 / 正式发表 ↗ 代码 / Artifact ↗
前几位作者 / 通讯Xuan-Phi Nguyen, Shrey Pandit, Austin Xu, Caiming Xiong, Shafiq Joty
署名机构Salesforce AI Research

Critical-Path-Aware Joint MoE Runtime Planning

Compute每 Replica 的 Token/Shape、Activated Replicas、Padded M Tiles、Grouped GEMM LatencyToken Count ≠ Weight Streaming ≠ 实际 GEMM 时间（TEMPO）
CommunicationDispatch/Combine、同步、跨 NVLink/RDMA、Buffer Copy、有效带宽越大吞吐并不保证越低 Decode TPOT（NVLinkOneSided）
PlannerSolver 延迟、采样/Trace Age、Reconfiguration Cost、GPU/CPU Synchronization高性能算法若每步需 100µs 可能不能部署（LPLB/Relief）
End-to-EndTTFT、TPOT、Goodput、P95/P99、Energy/Token、模型结果一致性只展示 Layer Kernel Speedup，不足以推导服务收益
Scale8/16/32+ GPUs，节点内/节点间 Topology 与不同 Model Shape单域 NVLink 结论不能直接移植跨节点 RDMA
建议的初始 Benchmark 实验矩阵

控制：Prefill Token [128,1024,8192]、Decode Active Token [1,16,64,256]；Routing Skew（均匀、Zipf、Trace-derived）；Replica Budget [0,1,2,4]；EP [4,8,16]；单域 NVLink 与跨节点分开；开启/关闭 CUDA Graph、量化/FP8；统计 ≥ 30 次有效重复的延迟分布，同时固定 Warmup/JIT 行为。上述为候选配置，不代表任何论文原始实验设置。

怎样做 Paper Novelty Check？

为每个想法建立五列表：新现象、现有方法为何失败、新的建模假设、新机制、对照最强 Baseline。至少把 TEMPO 的时间模型、OverlapAdvisor 的策略选择、MegaFlux 的动态复制、Relief 的低开销求解作为反例检验；如果只是它们的直接组合，需找到明确的‘组合改变原有最优性条件’的非平凡贡献。
