arXiv preprint · cs.DC / cs.LG

Abstract

Original Abstract Summary
KIWI exposes reverse offload as a programmable GPU-to-CPU invocation interface rather than a fallback. Its queue design targets sub-microsecond handoff and high operation rates; KIWI-P2P provides SHMEM-like primitives, while KIWI-EP uses workload-defined operations to redesign low-latency expert-parallel dispatch and combine.
中文摘要
KIWI 让 GPU kernel 以极低开销调用 CPU proxy 上的自定义操作，用 CPU 处理协议和网络控制、GPU 保留数据面计算。系统进一步构建 P2P 通信库与 MoE 专用后端，验证 reverse offload 在合适队列与 proxy 布局下可以优于 GPU 驱动控制。

Technical Analysis

Problem
现有 GPUDirect Async 路径把传输控制压在 GPU wave/thread 上；CPU proxy 常因共享队列争用、轮询成本和负载不均被当作慢速方案。
Method
为每 GPU 暴露可注册的 CPU handler，设计低争用 GPU→CPU 队列、动态 endpoint polling 与 NUMA-aware proxy placement；在其上构建 KIWI-P2P 与 KIWI-EP。
Architecture
GPU producer waves → KIWI invocation queue → pinned CPU proxy handlers → NIC/RDMA 操作 → GPU completion；KIWI-EP 把 token metadata packing、dispatch、combine 与动态 endpoint 轮询组织为 workload-defined 操作。
Key Innovation
核心新增量不是单一通信原语，而是把 reverse offload 变成可编程接口，使通信协议可按 EP workload 重写，并把 GPU 控制开销转移到高并发 CPU proxy。
Experiments
AMD MI300X 集群；每节点 8×MI300X 192GB、2×56-core Xeon 8480+、8×400Gb/s ConnectX-7 RoCE。数据点至少 3 次取中位数；与 RCCL GIN、NVSHMEM 等 GDA 路径及 EP 后端比较。

Key Results

来源报告：KIWI queue 在 1,024 producer waves 下保持约 0.12μs device-side push；KIWI-EP 的 EP 通信时延相对最佳既有 AMD 后端最高降低 2.3×，并使 vLLM time-per-output-token 最高改善 29%。这些最大值来自特定消息规模、模型与并行配置，不能外推为所有场景统一收益。

Editorial Assessment

Why It Matters
GPU 发起通信正在进入 MoE、persistent kernel 和细粒度 runtime；KIWI 证明 CPU proxy 并非天然慢，只要调用层把队列与轮询设计为硬件拓扑的一部分。
Limitations
结果集中于 AMD MI300X/RoCE；CPU core、NUMA 与 proxy 预算是实质成本。跨 NVIDIA/CUDA 的可移植性及大规模拥塞下的稳定性尚未披露。
Editor Note
编辑判断：这是当日系统新增量最大的工作。代码公开、硬件与对照充分，但 29% 是端到端上界而不是普遍保证。

Related Work

01 · RCCL GIN同为 GPU-initiated 通信；GIN 让 GPU 承担控制，KIWI 让 CPU proxy 执行可编程 handler；新增量是低开销 reverse-offload API。
02 · NVSHMEM同为 kernel 内发起通信；NVSHMEM 提供设备端 PGAS 原语，KIWI-P2P 以 CPU proxy 实现并扩展 workload-defined 操作。
03 · DeepEP同为 MoE dispatch/combine 优化；DeepEP 主要是 GPU 通信 kernel/传输协议，KIWI-EP 将控制与数据路径跨 CPU/GPU 重构。

Abstract

Original Abstract Summary
DexAttention co-designs GPU-accelerated topology-aware assignment, lightweight greedy scheduling and a persistent GPU executor for distributed sparse attention. The planner stays coarse while runtime readiness signals enforce fine dependencies, supporting static and dynamic per-head masks across several attention kernels.
中文摘要
分布式稀疏注意力即使少算了 tile，也可能仍传输大量 KV，且动态 mask 的重规划本身会吃掉收益。DexAttention 用 GPU 聚类平衡复用与负载、CPU 调度粗粒度传输，再由常驻 kernel 按就绪信号派发细粒度任务。

Technical Analysis

Problem
Ring/AllGather 可能传输未被稀疏 mask 使用的 KV；已有 mask-aware planner 耗时从几十毫秒到数百秒，难以服务动态 per-head mask。
Method
分层聚类 query rows，按 KV 共享度与 load cap 分配；用计算收益/传输成本排序消息；必要时重新切分 KV，并让常驻 controller block 追踪就绪与 partial output。
Architecture
GPU assigner（CUDA Graph）→ CPU coarse scheduler → 每 GPU 一个 persistent pass kernel（1 control block + compute workers）→ NVSHMEM inter-node + copy-engine intra-node；ready signals 解开细依赖。
Key Innovation
规划无需模拟完整时间线：粗 schedule 只给优先级，executor 用运行时 readiness 解释它，从而把动态规划压到 6–23ms并避免碎片化 kernel launch。
Experiments
4 节点、16×RTX A5000，节点内 PCIe、每节点 1×200Gb/s InfiniBand；六类 workload，覆盖 Qwen、MiniCPM、Llama 与 Wan，32K–256K，静态/动态 mask、训练与 prefill。

Key Results

来源报告：11 个训练配置相对最快适用 baseline 的端到端几何平均加速 1.39×；动态视频注意力包含规划时相对 Ring Attention 为 2.11–2.37×。动态 LLM prefill 的某些配置仅 0.98–1.07× Ring，说明收益取决于 mask 与通信占比。

Editorial Assessment

Why It Matters
长上下文的真正系统难点从稀疏 kernel 延伸到跨 GPU 数据依赖；DexAttention 给出 planner/runtime 分工清晰且代码可复现的答案。
Limitations
硬件为较老 A5000+单 NIC 节点；某些 dynamic LLM prefill 几乎无收益，Q 重分配可能反而更贵。未验证 H100/Blackwell/NVLink fabric。
Editor Note
编辑判断：可复现性与负结果披露优秀；S+ 来自完整的 planner—scheduler—executor 闭环，而不是某个峰值数字。

Related Work

01 · Ring Attention共同点是 context parallelism；Ring 固定循环 KV，Dex 根据 mask 重分配 tile 与数据，新增在线规划和 2D Q/KV movement。
02 · MagiAttention共同点是 mask-aware distributed attention；Magi 的规划/接口更受 shared-head/range 限制，Dex 支持动态 per-head mask 与毫秒级计划。
03 · DeepEP / COMET共同点是 GPU-driven 通信与计算重叠；它们面向 EP/collective，Dex 把 persistent execution用于稀疏 attention 的不规则依赖。

Abstract

Original Abstract Summary
BubbleTea identifies persistent 8–13% prefill bubbles caused by uneven expert routing even after load balancing. It predicts each GPU’s bubble from layer-level routing and admits compiler-derived fine-tuning chunks that reuse serving weights, protecting latency with early-close margins.
中文摘要
MoE 的路由偏斜会让轻载 GPU 等待最忙 GPU。BubbleTea 不把这段时间视为不可用，而是为每层每卡估计空泡，并运行足够短的微调计算片段；编译器切分反向图，在线调度器则根据预测窗口和安全裕量准入。

Technical Analysis

Problem
传统 colocation 以 iteration/forward pass 为单位对所有 GPU 同步让渡资源，无法利用 EP 层内每卡不同的空闲窗口。
Method
离线 compiler 从微调图导出可独立执行的短 chunk；在线从 router token assignment 预测每卡 bubble，预留早停 margin，并保持 ready work 以避免空泡内调度延迟。
Architecture
vLLM BF16 MoE serving → router-aware per-layer predictor → per-GPU admission → fine-tuning chunk runtime（复用已驻留权重）→ optimizer state；服务优先并可提前关闭窗口。
Key Innovation
将 colocation 调度粒度从整次迭代降到 MoE layer×GPU，并通过权重复用把 bubble-filling 变为真正细粒度而非另启一套模型。
Experiments
单节点 4×A100-SXM4-80GB NVLink；Qwen3-30B-A3B、Qwen1.5-MoE-A2.7B、DeepSeek-V2-Lite；1K–32K arXiv prompts、32 output tokens、Azure 两类 10 分钟 production traces；Alpaca 微调。

Key Results

来源报告：相对 LLMStation 的微调吞吐为 1.9–6.2×；50/63 个 steady workloads 中 p90 inference latency 保持在 serving-only 的 10% 内。生产 trace 中为 3.3× LLMStation、14× stock trainer+CUDA MPS，p90 误差在 7% 内。不同数字来自不同负载，不合并。

Editorial Assessment

Why It Matters
它揭示 EP 不均衡不只是要消灭的损耗，也可作为可调度资源；这对 inference/training colocation 和在线适配特别重要。
Limitations
仅单节点 4×A100；代码未披露/未核实。细粒度编译与 optimizer-state 内存成本对更大模型、多节点 EP 尚未验证。
Editor Note
编辑判断：系统洞见强、实验矩阵大，但缺少公开实现，因此评分低于两项 S+ 工作。

Related Work

01 · LLMStation共同点是 inference+fine-tuning colocation；LLMStation按迭代挂起，BubbleTea按层按 GPU 填空泡。
02 · EPLB共同点是缓解 expert routing 不均；EPLB重平衡负载，BubbleTea利用重平衡后仍存在的残余 bubble，两者可组合。
03 · CUDA MPS共同点是共享 GPU；MPS不理解 router/层边界，BubbleTea用服务语义做准入并复用权重。

Abstract

Original Abstract Summary
Cap-and-Track combines durable priority queues, fail-fast admission at the constrained resource and a stateful refusal-driven dispatcher. It avoids predicting output length or maintaining a fleet-wide fixed rate, and is evaluated through real-engine replay and large production A/B tests.
中文摘要
异步 LLM 任务可等待，但不应在引擎内部无界排队。该系统让多余请求留在持久优先队列，Cap 在资源入口快速拒绝，Track 只看明确的容量拒绝率做乘法升降速，以适配扩缩容、共享 provider 竞争和 token mix 变化。

Technical Analysis

Problem
固定 request rate 会随 fleet resize、输出长度与共享容量变化而失效；深引擎队列占用连接/KV 并让超时与重试失控。
Method
每 replica/provider 设置 fail-fast Cap；每 15 秒按目标拒绝率更新队列 dispatch rate，配合 leader、consistent-hash placement、restart freeze、local retry 与优先级。
Architecture
FOQS durable queues → Track workers/leader → gateway → provider admission 或 per-replica model-server Cap → vLLM engines；429 仅作为 capacity signal，拒绝任务回本地 ready queue。
Key Innovation
不估计输出 tokens、不读取 engine metrics，用资源端明确拒绝闭环控制 fleet-level dispatch；将短队列、持久优先级和状态化控制器组合为生产设计。
Experiments
真实 H100/MI300X/MI350X fleets，峰值超过 4,000 accelerators；含 real-engine controlled replay、同流量 production A/B 和 6 类 workload。部分结果为观察性窗口，论文明确列出 caveat。

Key Results

来源报告：classifier 在相同生产流量下使用比固定速率前身少 43% 的 H100；稳定容量 replay 中 goodput 距调优 fixed-rate 不足 1%，拒绝占比约为其四分之一；在线每天 >3 亿请求，峰值 24 小时 11 亿。低优先级任务在 backfill 峰值等待更久。

Editorial Assessment

Why It Matters
这是少见的、把 engine queue limit 与跨 fleet feedback controller 联合验证的生产证据，直接对应 SLO、batch fullness 与弹性容量。
Limitations
适用于可异步等待且后端能快速、可标记拒绝的 workload；控制器对中等容量骤降反应较慢，且大量生产指标是 observational。无公开实现。
Editor Note
编辑判断：工程影响与证据规模极强；可复现性低，故不是 S+。43% H100 降幅不能脱离其 fixed-rate precursor 和 workload 解读。

Related Work

01 · vLLM queue limit共同点是限制引擎等待队列；vLLM是单引擎机制，Cap-and-Track增加持久队列和 fleet-level反馈调度。
02 · AIMD congestion control共同点是用拒绝/拥塞反馈调速；Track采用 MIMD 并以单容量域控制器避免多发送方公平问题。
03 · Orca continuous batching共同点是提升 batch 利用；Orca调度引擎内序列，Cap-and-Track决定多少异步工作应进入引擎。

Abstract

Original Abstract Summary
The paper reverse engineers a control-code field that appears widely in NVIDIA libraries but is not emitted by nvcc. Microbenchmarks identify barrier exemption and three programmable warp-priority marks, and a profile-guided binary optimizer inserts them without source or compiler changes.
中文摘要
研究通过指令级微基准识别出两套硬件调度机制：exempt 可让等待 barrier 的 warp 提前发射不依赖指令，start/tile/end 则调整 warp 优先级。随后系统用一次 Nsight trace 选择 kernel 并直接改写 cubin。

Technical Analysis

Problem
nvcc 无法表达 NVIDIA closed-source libraries 大量使用的控制字段，用户 kernel 因 barrier stall 与 warp 调度次优错失硬件能力。
Method
跨架构微基准定位 bits 语义；基于依赖与 loop 结构放置 exempt/tile/end；用一次运行 profile 筛选 CTA residency、wave 数和 wave duration 满足条件的 kernel。
Architecture
原始 cubin → 静态 SASS/CFG 分析 + Nsight Systems profile → mark placement → 二进制 patch → llama.cpp/vLLM 原框架加载；不改源码与编译器。
Key Innovation
首次把未公开字段从观察频次推进到跨四代架构的机制验证，并形成可作用于生产二进制的自动优化流程。
Experiments
6 款 NVIDIA GPU：A800、RTX4090、H20、H100、RTX PRO 6000、GB10；Qwen3-8B 与 Qwen3-30B-A3B，llama.cpp Q4_K_M、vLLM AWQ/GPTQ；对照同一 nvcc build。

Key Results

来源报告：代表性 kernel 最高 31.9%，llama.cpp/vLLM production kernels 最高 5.4%，端到端 LLM inference 最高 3.6%；优化版本通过 18,505 个 llama.cpp 与 10,267 个 vLLM tests。峰值来自不同 kernel/GPU，不合并。

Editorial Assessment

Why It Matters
编译器未暴露的 warp scheduling 能力仍可能影响生产 LLM kernel；二进制后优化提供了无需等工具链升级的验证路径。
Limitations
依赖未公开 ISA，驱动/架构演进可能破坏假设；代码与 optimizer 未披露/未核实；需要 profile，且端到端收益明显小于 kernel 峰值。
Editor Note
编辑判断：机制新颖且跨代验证扎实；因闭源 ISA 风险与无代码，保持 A+。

Related Work

01 · CuAssembler / MaxAs共同点是 SASS 级分析与改写；本工作新增未公开 control field 的跨代语义与自动 placement。
02 · Triton warp specialization共同点是显式调度与流水；Triton在编译层组织 warp roles，本工作在编译后改写硬件优先级。
03 · CUDA binary instrumentation共同点是无需源代码改写 cubin；本工作目标是 barrier/priority 性能，而非监控或正确性检查。

Abstract

Original Abstract Summary
MRPD replays domain experts’ RL logs in their original training order. It recomputes policy gradients on scored trajectories and distills final-expert distributions at logged prefixes, keeping the student close enough to the logging policies to remain quasi-on-policy during consolidation.
中文摘要
多领域专家整合通常让 student 再次运行环境并逐 token 调用 teacher，成本高且会继承最终专家漂移。MRPD 复用专家训练期间已有的轨迹、采样概率和奖励，并保留原步序，让日志成为课程而不是混合数据集。

Technical Analysis

Problem
MOPD 需要重新采样所有环境、等待最长 agent trajectory 并为每个 token 运行专家；参数合并又常牺牲某些领域。
Method
每步重放各专家同一步日志，按 logging policy 重算 clipped policy gradient；在每个 logged prefix 上用 final expert full distribution 做 dense KL；不调用环境或 reward model。
Architecture
ordered expert logs/object store → 单 trainer process → expert forward at logged prefixes → PG + dense KL → shared student；无 rollout actors、environment workers 与 reward services。
Key Innovation
把顺序本身视为保持 quasi-on-policy 的系统/算法条件；相同数据 shuffle 后性能下降，说明日志不是可任意池化的数据集。
Experiments
8×H100，三类长程 agent domain（reasoning/search/SQL），3 个专家各 300 steps、约 46 万 trajectories；16 个 held-out sets，对比 RAFT、GRPO、PPO、MOPD、MOPD+GRPO、soups、TIES。

Key Results

来源报告：MRPD 300 steps 约 9 小时，MOPD+GRPO 29 小时；仅为训练三个专家计算量的约 14%（约 1/7）。总体 held-out score 58.6，高于 MOPD 58.1、MOPD+GRPO 58.2 与 online GRPO/PPO 52.5/52.6。硬件与样本数固定，不能外推到更大模型。

Editorial Assessment

Why It Matters
post-training 成本往往由 rollout 与工具环境而非 trainer FLOPs 主导；MRPD 把历史日志从副产物变成可复用训练资产。
Limitations
要求专家与 student 共享初始化且有完整有序日志；只验证三领域和单一规模。dense expert forward 仍有成本，日志保存/隐私治理未展开。

Related Work

02 · REGEN共同点是回收专家 GRPO rollouts；REGEN池化过滤后离线训练，MRPD保留训练顺序并加入最终专家 dense target。
03 · TIES merging共同点是整合领域专家；TIES在参数空间无数据合并，MRPD重放行为轨迹，计算更高但总体得分更好。
