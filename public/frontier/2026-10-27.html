Abstract

Original Abstract Summary

DualPace is an LLM serving runtime that gives GPU-resident and CPU-resident requests independent scheduling authority. The CPU engine advances host-resident decodes with AMX kernels and may invoke GPU Dense Assist at stage boundaries, while profile-guided routing chooses the execution path. Evaluations compare the runtime against NEO and vLLM under decode-heavy traces.

中文摘要

论文识别出 CPU offload 的关键问题不是单纯算力不足，而是 CPU 请求只能等待 GPU 批次提供合适的重叠窗口。DualPace 将两类请求分给独立调度引擎，同时保留细粒度 GPU 协助，使 host memory 真正成为持续推进的解码层。

Technical Analysis

Problem

传统 CPU KV offload 仍由 GPU 迭代门控；prefill 减少后，CPU-resident 请求出现停顿，尾部 ITL 恶化。

Method

双调度器分别管理 HBM/DRAM KV 与请求队列；全局 KV 安全预算防止两端过量承诺；离线 profile 决定 CPU 本地计算或 GPU Dense Assist。

Architecture

GPU engine 负责全部 prefill 与 GPU decode；CPU engine 负责 host-resident decode，使用 oneDNN BF16/AMX。请求所有权不随 Dense Assist 改变，辅助只在显式模型 stage boundary 交换张量。

Key Innovation

把 scheduling authority 与 execution placement 解耦：CPU 请求可独立推进，又能选择性借用 GPU dense stages，而不会重新进入 GPU scheduler。

Experiments

公开论文给出 RTX 4090、12 physical-core Xeon Silver 4510、Llama-3.1-8B 与 2,000 条 Azure-Conversation trace；另覆盖 Azure-Code、不同 KV 容量与 CPU TP。对照为 vLLM 与开源 NEO。

Editorial Assessment

Why It Matters

当 HBM 紧张而 DRAM/CPU 尚有余量时，独立调度把“容量扩展”变成可持续吞吐，而非被 GPU 机会窗口限制的旁路。

Limitations

主要硬件是一台消费级 GPU 加 Sapphire Rapids CPU；收益集中在 decode-heavy 与 AMX 可用场景。代码链接未披露，跨多 GPU/多节点与非 Intel CPU 的可复现性未核实。

Editor Note

值得优先阅读的是“CPU 是否拥有自己的 scheduling clock”，而不只是某个算子快多少；这是异构 serving 是否真正解耦的判据。

03

共同点：动态 KV 管理与 continuous batching；区别：vLLM 仍以 GPU 为中心；新增量：DRAM KV 的独立执行层。

Abstract

Original Abstract Summary

RIPE studies which recurrent-depth KV planes must be retained during self-speculative decoding of looped language models. Sensitivity and geometric-ripening measurements motivate keeping only the deepest plane for settled prefix positions and all planes in a recent window. Pre-registered GH200 experiments evaluate fidelity, acceptance, memory, and fixed-budget throughput on Huginn and Raven-Llama.

中文摘要

循环语言模型让同一层块重复运行，导致每个 token 产生多层 KV plane。RIPE 发现旧前缀的深层 plane 已趋于稳定，因此只保留最深 plane；对最近窗口保留全深度，避免批量验证依赖 block boundary。

Technical Analysis

Problem

循环模型的权重很小，但每个 loop 都写 KV，使自推测解码在长上下文下被缓存容量而非权重限制。

Method

用扰动敏感度和 plane 几何收敛刻画“成熟度”；对 settled prefix 使用 deepest plane，对 W 个最近位置保留 full-depth planes。

Architecture

RIPE 嵌入 draft-then-verify 自推测解码：验证块落在 full-depth window 内，因此跨块验证不再依赖分块起点；旧位置以单 plane 参与注意力。

Key Innovation

缓存策略依据 loop depth 的信息成熟度而非 token age 做非均匀保留，并用预注册实验验证失败预测与尾部误差。

Experiments

NVIDIA GH200 96GB，PyTorch 2.14、CUDA 13.0、BF16、greedy decoding；Huginn-0125 与 Raven-Llama，GSM8K 8-shot 和 AlpacaEval prompts；九个预注册 batch。

Editorial Assessment

Why It Matters

looped/recurrent-depth 模型若要获得权重复用优势，必须解决 KV 随 loop 数线性膨胀；RIPE 给出了可验证的容量路径。

Limitations

适用对象是 looped LM，不直接外推到普通 Transformer。Huginn deepest-only 有少量高误差尾部；作者未给独立代码仓库，部分调度复用 WaveFront 代码。

Editor Note

论文把负结果写得很清楚：简单截断浅层 plane 的直觉是反的。需要关注模型间成熟度差异，而不是把 11.9% 内存当成普适常数。

02

03

共同点：looped LM 与 deepest-plane 经验；区别：RIPE 显式处理 Huginn 的误差尾部；新增量：recent full-depth window。

Abstract

Original Abstract Summary

COPE factors MoE offloading into expert-residency and execution-strategy axes, then profiles combined operators on a target machine and combines them with offline routing traces. The resulting emulator ranks candidate policies before integration, reducing prediction error and implementation effort across heterogeneous model-platform combinations.

中文摘要

MoE offload 的最佳方案取决于专家稀疏度、显存、CPU/GPU 算力和主机互联。COPE 不再假设一个策略适配所有机器，而是把 resident policy 与 execution strategy 正交组合，并通过目标机算子 profile 估计 TPOT。

Technical Analysis

Problem

不同模型与硬件会颠倒 offload 策略排名，而逐个实现、完整跑通所有候选的工程成本过高。

Method

Policy Matrix 分解 expert residency 与执行方式；Virtual Heterogeneous Machine 测量组合算子 schedule，再与离线路由 trace 合成性能。

Architecture

trace collector 记录 token-to-expert 行为；硬件 profiler 建立 atomic/combined operator cost；emulator 组合 transfer、CPU/GPU execution 与 overlap，输出候选 TPOT 排名。

Key Innovation

把 offloading policy 变成可组合、可执行的二维设计空间，并以少量目标机测量预测完整运行时，而非只做解析 roofline。

Experiments

A100、RTX 4090、RTX 5090；覆盖 Qwen/Mixtral 等 MoE 与多种稀疏模式；对比 llama.cpp、vLLM/SGLang offloader 与学术 offloading policies。详细样本数以论文表格为准。

Editorial Assessment

Why It Matters

MoE edge/单机部署的最大风险是策略在另一台机器上失效；COPE 将“先选策略、后投入实现”变成系统化流程。

Limitations

论文关注预测与选择，不是新的 production serving runtime；离线路由 trace 可能遗漏 workload drift，公开代码链接未披露。

Editor Note

它的价值在 design-space triage，而非单点极致性能。若工具开源，可成为 MoE runtime 在新硬件上的前置评估层。

Abstract

Original Abstract Summary

This study characterizes when Hopper TMA outperforms cp.async and when cluster multicast helps relative to unicast or distributed shared memory. It grounds the analysis in FlashAttention-3 paged-KV dispatch and CUTLASS GEMM, using H100 microbenchmarks and a B200 extension to derive predictive kernel-design guidance.

中文摘要

TMA 能把大块 global-to-shared copy 交给硬件，但 descriptor、传输粒度和 cluster multicast 都有固定成本。论文围绕 FA3/FlashInfer 的真实选择，说明为何 paged KV 小块或低计算量场景仍可能应使用 cp.async，并比较 multicast 与 DSM。

Technical Analysis

Problem

厂商文档说明 API，孤立 microbenchmark 给峰值，却不能回答一个具体 operand 在真实 kernel 中该选哪条加载路径。

Method

拆解 FA3 forward 中的 TMA/cp.async/DSM 选择；扫 transfer size、KV page、datatype、model shape、phase 与 multicast cluster；再以 CUTLASS GEMM 交叉验证。

Architecture

H100 上运行独立 harness 与生产 kernel variants；分析 global→shared pipeline、cluster multicast 和 DSM broadcast；B200 SM100 用 CUTLASS GEMM 验证规则迁移。

Key Innovation

把 TMA crossover 与 paged-KV allocator 参数连接起来，并将 multicast 与 DSM 视作竞争的 cluster-broadcast primitives。

Experiments

NVIDIA H100 为主、B200 扩展；FlashAttention-3 forward/paged KV、FlashInfer 设计选择、CUTLASS GEMM；公开摘要未给每个 sweep 的统一数值，报告按条件化结论引用。

Editorial Assessment

Why It Matters

attention/megakernel 优化越来越取决于数据移动机制；这类条件化规则比“始终使用新指令”更能指导 vLLM、TensorRT-LLM 与 FlashInfer。

Limitations

以两代 NVIDIA GPU 为限，不覆盖 AMD/其他加速器；结论高度依赖 kernel shape 与软件版本，且未披露独立代码仓库。

Editor Note

不要把它解读为 TMA 的统一加速榜。真正新增量是：page size 不只是 allocator 参数，也会改变 kernel 能否走 TMA 路径。

Abstract

Original Abstract Summary

The work implements end-to-end MXFP8 LLM reinforcement learning in verl with Megatron and Transformer Engine for training and vLLM or SGLang for rollout. It measures policy mismatch, speed, and failure modes on Blackwell B200 using dense and MoE Qwen models, and introduces seven synchronization invariants plus runtime and fault-injection checks.

中文摘要

低精度 RL 不只是训练快不快：rollout engine 与 learner 必须表示同一策略。该工作把两端放在共享 MXFP8 grid 上，并系统测量 KL、一致性、微批固定开销和同步故障，给出何时低精度真正划算的边界。

Technical Analysis

Problem

sampler/learner 是不同实现，量化 grid、derived layouts 与权重同步稍有偏差就把 on-policy RL 变成静默 off-policy。

Method

共享 microscaling grid；同步后重建 sampler layouts；保留必要高精度层；定义七项权重同步条件并运行 byte-level、quantizer 与 fault-injection checks。

Architecture

Key Innovation

把速度、一致性和正确性放进同一个端到端实验，不用“FP8 峰值 FLOPS”替代 RL policy matching 证据。

Experiments

NVIDIA B200；单 seed、最多 60 steps；dense/MoE、不同 micro-batch token 数；固定权重比较、step trace、七类真实故障与 CPU fault injection。

Editorial Assessment

Why It Matters

在线 RL 的吞吐优化若破坏策略一致性可能抵消训练收益；该工作提供可执行的同步审计清单与明确 break-even。

Limitations

全部运行单 seed 且最多 60 steps，作者明确不声称最终模型质量；无 quantized KV 时 BF16 仍显著更一致，结论也依赖 Blackwell MXFP8。

Editor Note

这是“负结果也重要”的系统报告：短序列 dense 可能更慢，且共享 grid 不能自动胜过 BF16。最值得复用的是不变量与检查，而不是 24% 单项数字。
