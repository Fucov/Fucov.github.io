Abstract

Original Abstract Summary

Lachesis observes that an agent harness determines segment lifetimes along temporal, structural and inter-worker axes. It places short-lived KV segments in HBM and long-lived segments in high-bandwidth flash, then frees each segment at its last-use boundary to reduce flash writes.

中文摘要

Agent 会跨多轮、跨子代理长期保留 KV，容量压力把系统推向 HBM 与闪存分层，但闪存耐久度成为新瓶颈。Lachesis 不只看当前空闲块，而是利用 harness 暴露的生命周期，在写入时决定介质。

Technical Analysis

Problem

传统 HBM-first 只按容量溢出，短寿命块可能挤占 HBM，迫使大量本可由 HBM 吸收的写入落到寿命有限的闪存。

Method

harness 生命周期标注、worker lifetime prediction、HBM/HBF admission、last-read boundary reclaim。

Architecture

Agent harness → lifetime classifier/predictor → tier allocator → HBM/HBF blocks → boundary-triggered free。

Key Innovation

把 agent 程序结构作为 KV 介质放置信号，并把 flash endurance 纳入 serving policy。

Experiments

单/多 agent traces、两级内存 trace replay、tight-SLO admission 与 24×7 endurance 模型。

Editorial Assessment

Why It Matters

Agent serving 的状态规模正从单请求 KV 变成跨会话对象；该工作给出面向新型高带宽闪存的具体放置原则。

Limitations

主要为 trace-driven simulation；依赖未来/新型 HBF 特性和 harness 暴露寿命；预测误差、真实故障与写放大仍待系统实测。

Editor Note

今日 Must Read。重点不是“用闪存”，而是把 agent 语义转换为可执行的 KV 生命周期控制面。

Abstract

Original Abstract Summary

DySCo keeps model shards and their KV caches resident across edge and cloud. Its dyForward executes configurable contiguous layer ranges without weight reloads, while depth-synchronized batching advances heterogeneous requests to a common depth and batches their shared suffix.

中文摘要

边缘设备算力差异导致切分层不同，云端收到的请求处于不同网络深度，普通 batching 无法合并。DySCo 将“模型深度”加入调度状态，在不重载权重的前提下复用后缀。

Technical Analysis

Problem

异构切分导致云 GPU 出现 inter-token idle gap，且不同深度请求不能直接连续批处理。

Method

resident dynamic shards、local KV、dyForward layer-range executor、depth-synchronized batching。

Architecture

Edge shards + local KV → network → cloud request-depth queues → advance-to-deepest → shared suffix batch。

Key Innovation

把 batch 对齐维度从到达时间/序列长度扩展到模型深度。

Experiments

Qwen/Llama 四种配置、异构 edge devices、本地与 WAN 链路、Poisson arrivals、16 个 warm workers。

Editorial Assessment

Why It Matters

为真实异构边云协同推理补上运行时与调度层，而不仅是离线选择 split point。

Limitations

需保持多段权重常驻；网络抖动和边缘故障影响未充分展开；尚未与生产 serving engine 深度集成。

Editor Note

代码公开，结果清晰。特别值得复现 idle-gap 对后续 GPU forward 的非等待时间影响。

Abstract

Original Abstract Summary

NeMo-DCR exploits the small fraction of BF16 values whose stored bits change after each RL step. Owners project sparse changes into canonical checkpoint coordinates, encode them with exact XOR masks or overwrites, stream them through object storage or relay trees, and apply them through the serving runtime native loader with retry-safe joint commit.

中文摘要

Agentic RL 将训练和 rollout 分离后，每一步都要跨集群同步策略。NeMo-DCR 发现实际只有约 0.6–1.2% BF16 元素改变存储位，因此把 refit 改造成稀疏、流式、位精确且能从中断恢复的事务。

Technical Analysis

Problem

全量 checkpoint 在万亿参数/跨地域场景耗时数十分钟；现有 delta 方法又常损失位精确、原生布局兼容或故障恢复。

Method

change ownership、canonical projection、residual conversion、mixed XOR/overwrite compression、relay tree/object storage、joint commit。

Architecture

Training shards → owners/delta builder → streamed transport → native serving loader → in-place receivers → coordinator commit。

Key Innovation

同时满足 bit-exact、delta、native placement、cross-cluster decoupling 和 mid-refit recovery 五项要求。

Experiments

Qwen3/Nemotron，30B–1T extrapolation and measured runs，3%/5% stress rate，receiver-kill recovery，GRPO trajectories。

Editorial Assessment

Why It Matters

把 rollout 与训练放到不同机群/地域的 agentic RL 从网络上变得可行，并避免 policy mismatch 破坏训练稳定。

Limitations

依赖 BF16 变化稀疏性、canonical mapping 与 loader hooks；1T 结果含模型化/缩放部分；baseline 占用额外 host memory。

Editor Note

本期首读。代码已进入 NVIDIA NeMo RL PR，且论文明确披露边界、恢复语义与 payload 构成。

Abstract

Original Abstract Summary

TRANSIT interposes in user space to extend GPU memory with CPU DRAM through UVM, without modifying applications, frameworks, schedulers, drivers or operating systems. It augments reactive migration with page-granular prefetch and zero-copy policies and evaluates dense and MoE training up to 64 H100 GPUs.

中文摘要

训练常为满足显存容量被迫 scale-out，GPU 数增加又放大 collective。TRANSIT 反向做 scale-in：让主机 DRAM 承担冷页容量，并用零拷贝避免不必要的数据迁移。

Technical Analysis

Problem

框架 offload 侵入性强、粒度粗；默认 UVM 在多节点训练中的效率和可部署性不足。

Method

user-space interception、UVM policy override、page-granular prefetch、direct L2 zero-copy、runtime policy selection。

Architecture

Unmodified trainer/framework → interposition layer → UVM page manager → HBM/CPU DRAM → RoCE collectives。

Key Innovation

无需特权改动即可在多节点/多并行配置下做透明 scale-in，并把减少节点与降低通信耦合起来。

Experiments

Dense/MoE，多种 parallelism，最多 64×H100，RoCE，对照 TorchTitan、ZeRO-Offload、ZeRO-Infinity。

Editorial Assessment

Why It Matters

把“显存不够就加 GPU”改成更经济的容量-通信联合优化，尤其适合供应受限集群。

Limitations

Abstract

Original Abstract Summary

NCCL M2N derives exact transfer regions and a global schedule from source and destination meshes and tensor placements. It balances source traffic across destination leaders, sends one inter-domain copy, fans out locally over NVLink and overlaps network transfer with replication.

中文摘要

Technical Analysis

Problem

Method

Architecture

Key Innovation

Experiments

Abstract

Original Abstract Summary

RelayMoE replaces the full all-to-all dispatch buffer with a ring execution model that adaptively circulates experts or tokens based on communication volume. Each hop computes locally and releases reconstructed intermediates during backward, enabling selective attention recomputation and larger batches or sequences.

中文摘要

高 top-k、更多专家和长序列让 MoE dispatch buffer 成为峰值显存主因。RelayMoE 用环形流式执行把全量展开缓冲变成逐 hop 工作集，并让重算与释放自然对齐。

Technical Analysis

Problem

标准 all-to-all 需要同时物化 k 倍 token buffer，MoE block 而非 attention 决定 OOM 边界。

Method

ring dispatch、expert/token adaptive routing、communication-compute overlap、hop-wise MoE recompute、selective attention recompute。

Architecture

Routed tokens → ring planner → circulating experts/tokens → local expert compute → hop-wise backward/release。

Key Innovation

把 EP dispatch 从全量交换改成可选择数据移动对象的流式 ring，并联合优化 MoE 与 attention 重算。

Experiments

30B–57B production MoE、多 expert/top-k 配置、单层与全模型、同显存预算对照 Megatron-LM。

Editorial Assessment

Why It Matters

针对现代高 top-k MoE 的真实显存尖峰，能把节省转成更长序列或更高吞吐。

Limitations

ring 在大规模/弱互连上的尾 hop 和负载不均风险；代码未明确公开；质量收敛与故障处理披露有限。

Editor Note

强结果但需看规模曲线。尤其应比较 DeepEP/NCCL-EP 在相同 memory cap 下的端到端表现。
