Venue

TensorRT-LLM core code · PR #21822

Abstract

Original Abstract Summary

TensorRT-LLM adds three opt-in KVCacheManagerV2 disk-tier optimizations: prioritized parallel SSD I/O, retained immutable SSD copies after restore, and background write-through from host memory. The PR reports a four-hour agentic replay and compares the native tier with Mooncake under disclosed conditions.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

原 SSD 传输在 CUDA host callback 中串行执行，restore 会被 eviction write 阻塞，且恢复后的不可变页下一次驱逐还要重写。新实现以 thread pool 和 stream wait flag 保持顺序，读优先分片调度，并复用已提交页的 SSD 副本；写穿仅占用空闲 SSD slot。

Technical Analysis

Problem

长时 agentic 会话使 KV 在 HBM、host 与 NVMe 之间频繁迁移；串行 pread/pwrite、重复写和 restore 关键路径写入导致 TTFT 长尾。

Method

最多 4 MiB I/O 分片；read→required write→background write 优先级并带防饥饿阈值；restore 后保留 immutable committed page；GPU→host 时机会式异步写穿。

Architecture

HBM KV ↔ 160 GiB host tier ↔ 1 TiB local NVMe RAID0；process-wide I/O pool、cuStreamWaitValue64 completion flag、1 GiB background queue cap 与 LRU retained-copy reclamation。

Key Innovation

把 SSD tier 的调度、复制语义和背压一起纳入 KV manager，而不是把 NVMe 当作阻塞文件副本。

Experiments

GLM-5.3、FP8 KV、8×GB300 节点；disagg 4P（4×DEP4）+4D（1×DEP16）；Kernel Factory 4 小时多轮 agentic coding trace，800 并发、300–2400 s 窗口。每配置仅 1 次；Mooncake v0.3.13 两次。

Editorial Assessment

Why It Matters

层次 KV 的价值取决于长尾而不只是带宽。该工作把 SSD 写入从 restore 关键路径移出，对多轮 agentic serving 更直接。

Limitations

每个 native 配置仅一轮，SSD 未填满；review 后新增的 1 GiB queue cap 未纳入原测量；选项默认关闭，且不同 node/runtime revision 使 Mooncake 吞吐比较只能视作近似持平。

Editor Note

S 级。系统设计、失败语义、测试覆盖和现实负载披露充分；单轮基准与未满盘状态要求保守解读。

共同点是 host/SSD 远端缓存；本作是 TensorRT-LLM 原生本地 tier，并以关键路径调度为核心。

共同点是 GPU—CPU—SSD 层次；本作新增 retained copy 与优先级分片 I/O。

SGLang core code · PR #50306–#50311

Abstract

Original Abstract Summary

A six-PR SGLang stack removes host stalls from GDN prefill, runs state operations in place, vectorizes state entry movement, performs eligible arena compaction on device, batches slot/page hand-outs, and caches admission work. It reports controlled H200 throughput and host/GPU idle measurements.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

栈内从 GDN prefill 到 unified allocator 全链路改造：预热 FlashInfer 变体、state pool 原地执行、word-wide clear/copy、device-only end packing、批量 bind/unbind/lease，以及 admission demand/pricing 复用。最后一项明确不宣称吞吐增益，而是减少 host 时间。

Technical Analysis

Problem

hybrid 模型每轮在 state slot 与 KV page 间交换容量；host .tolist()、多次小分配、staging launch 和重复 pricing 会让 scheduler 等待 forward，随后 GPU 再等 host。

Method

用 fence-safe device kernels 完成可判定的 end packing；合并 state/tracking slot 分配和 page bind-zero；复用每轮 demand、evictable credit 与 pricing feasibility；原地 GDN state 更新。

Architecture

Scheduler admission → unified chain allocator → shared state/KV arena → device pack/rebind → in-place GDN prefill → batched checkpoint leases；必要的固定页/传输场景仍走 host path。

Key Innovation

将 stateful serving 的“内存布局决策”从零散 host round-trip 改造成可在设备上完成且按 admission pass 缓存的协议。

Experiments

单 H200，Qwen3.5-4B，torch 2.14.1+cu130、Triton 3.8、FlashInfer 0.7.3；random 1024/256 c256 与 c16，shared-prefix 2048+128→128；3 次 server start，每次丢弃首轮后取两轮，n=6。

Editorial Assessment

Why It Matters

GDN/SSM 类模型把服务状态变成一等资源；如果 scheduler 每次容量决策都读回 host，统一内存只会把碎片问题转成同步问题。

Limitations

仅 H200、单模型与特定负载；六项叠加难以独立归因。PR 页面部分 CI 状态未完整通过或未运行，AMD 路径并非实测对象。

Editor Note

S 级。跨 allocator、kernel 与 scheduler 的系统闭环完整，且诚实区分显著结果与噪声；仍需更多模型和多 GPU 验证。

LMCache / HiCache

共同点是分层缓存；SGLang 栈关注同一 GPU arena 内 state 与 KV 的交换。

Venue

vLLM core code · PR #65658

Abstract

Original Abstract Summary

vLLM adds an opt-in ROCm pipeline-parallel handoff using SDMA copy engines and a three-slot IPC ring with shared ready/freed counters. The design reduces GEMM interference during stage transfers and reports a two-MI355X MiniMax workload.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

传统 peer copy 会与 GEMM 抢同一执行资源。新路径在 PP2/TP1 同节点上用 SDMA 做 stage tensor copy，生产者与消费者通过共享内存计数器管理三槽 ring 的 ready/freed 生命周期。

Technical Analysis

Problem

pipeline stage 交接若走普通 GPU copy/NCCL，会在传输期间显著干扰下一轮 GEMM，降低 PP run-ahead。

Method

建立跨进程 IPC buffer 与 3-slot ring；sender 以 SDMA 发起异步 copy，counter 表示 slot 就绪与释放；consumer 避免覆盖仍在用的数据。

Architecture

PP stage 0 output → SDMA copy engine → IPC ring slot → shared-memory counters → PP stage 1 input；计算引擎继续运行。

Key Innovation

用专用 copy engine 与有界 ring 把数据面从计算 stream 分离，并把 slot 生命周期显式化。

Experiments

2×MI355X、gfx950、MiniMax-M3.1-Flash、TP1×PP2、eager；16k prefill steps，4 轮交替实验；另有 copy/GEMM 干扰微基准。

Editorial Assessment

Why It Matters

PP 的性能瓶颈常不在纯带宽，而在传输对计算的干扰；SDMA 把硬件资源隔离用于服务路径。

Limitations

仅 gfx950、PP2/TP1、同节点 eager；CUDA graph、多 PP middle stages 与跨节点未支持，opt-in 默认关闭。

Editor Note

A+。微基准与端到端一致，工程边界诚实；适用拓扑较窄。

Venue

PyTorch core code · PR #204533

Abstract

Original Abstract Summary

This merged PyTorch change completes NCCL2 futures on the collective stream instead of synchronizing the caller stream. It preserves ordering for waits, callbacks and aliased all-gather outputs while restoring communication–computation overlap for DDP.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

旧 nccl2 在 DDP 每个 bucket 发起 all-reduce 后调用 get_future() 时立即阻塞当前 stream，导致反向计算无法继续。新实现把 future 的事件记录在 collective stream，并补齐 blockCurrentStream、barrier 与别名 all-gather 的顺序语义。

Technical Analysis

Problem

DDP 默认通信 hook 对每个 bucket 立即调用 get_future()；nccl2 内部 synchronize() 使调用 stream 等到 collective 结束，系统性消除 overlap。

Method

在 NCCL stream guard 下完成 future；无设备输出的 barrier 保留 synchronize；显式修复依赖旧隐式同步的 blockCurrentStream 与 staged all-gather copy。

Architecture

Backward bucket → NCCL2 all-reduce stream → future event on collective stream → continued caller-stream backward compute → wait/then consumer ordering。

Key Innovation

不是新增 collective，而是修正异步 API 的 stream contract，使 future 表示“可等待的完成事件”而不是“创建即同步”。

Experiments

Qwen2-7B、HF Trainer、BF16、seq 512、batch 1、gradient checkpointing、500 steps；4×MI355X ROCm。同一源码有/无 patch；另做 2-rank 512 MiB all-reduce overlap 微基准。

Editorial Assessment

Why It Matters

通信库若在 future 创建点隐式同步，所有上层 DDP bucketization 与 overlap 设计都会失效；该修复恢复 PyTorch 分布式的关键性能语义。

Limitations

性能只在 ROCm/MI355X 上测量，虽然路径并非 ROCm 专属；未来对象的 input lifetime 行为有变化，释放发生在 wait、blockCurrentStream 或后续 collective。

Editor Note

S 级。问题根因清晰、复现完整、吞吐与微基准相互印证；跨 CUDA/NVIDIA 的实测仍待补。

Abstract

Original Abstract Summary

DeepSpeed adds an opt-in AutoEP backward schedule that returns expert input gradients early, starts the asynchronous DeepEP combine, and computes deferred expert weight-gradient GEMMs concurrently. An SM carveout prevents persistent grouped GEMMs from starving communication.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

原 grouped GEMM 同时算 dX/dW，之后才启动 dX combine；profile 显示 DeepEP 通信期间没有计算。新路径用 slot 延迟 dW，先发 async combine，再在 compute stream 运行 dW，并通过 comm_num_sm carveout 给通信留 SM，最后等待 event。

Technical Analysis

Problem

MoE expert backward 中 dW 与 dX combine 数据独立却串行，persistent grouped GEMM 又可能占满 SM，让理论 overlap 无法实际发生。

Method

自定义 deferred backward 立即返回 dX、保存 dW work；DeepEP dispatch 启动 async combine；withheld SM 的 grouped GEMM 计算 dW；finally 恢复 carveout 并等待通信事件。

Architecture

Expert forward → backward dX early return → DeepEP combine on comm path || deferred dW grouped GEMM on compute stream → event join → ZeRO gradient handling。

Key Innovation

把数据依赖重排与 SM 资源隔离组合；仅发异步通信不足以获得 overlap，必须避免 GEMM 吞满所有 SM。

Experiments

Qwen3-30B-A3B、8×H100、EP8、micro-batch 4、16 accumulation、seq 4096、DeepEP、reentrant checkpointing、fused gate+up；30 steps、10 warmup。另有 402 个 H100 test 与 4 GPU 梯度 parity。

Editorial Assessment

Why It Matters

MoE 训练常受 AllToAll/combine 与专家 GEMM互相争抢影响；该工作说明 overlap 需要同时设计依赖图和 GPU 资源配额。

Limitations

仅支持 DeepEP、AutoEP>1、torch grouped_mm、ZeRO 1/2；拒绝 ZeRO 0/3、Triton grouped GEMM 与高阶导数。性能测量是此前等价 benchmark patch 的复用证据，最终 merge tree 未重跑完整 sweep。

Editor Note

S 级。方法与 profile 根因一致，守卫清晰且有端到端量化；支持矩阵窄、收益依赖 comm SM 预算。
