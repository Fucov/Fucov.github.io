Abstract

Original Abstract Summary（英文概述，非原文）

PackLoop changes how recurrent-depth language models arrange speculative work under load. It groups positions inside a request-loop row and uses a cost model to decide when to advance the deeper loops. The evaluation compares the layout with competing schedules over different GPUs, loads and context lengths.

中文摘要

循环模型自推测在单请求时有效，但并发下把位置铺到不同循环层级会重复读 KV。PackLoop 改为在同一行内积攒位置，深轮成块推进，并根据成本决定何时放行。

Technical Analysis

Problem

批量大时瓶颈转向请求×循环层级的 KV 访问；减少串行前向，并不自动减少每轮访问。

Method

深轮积攒候选位置，第一轮可附带上下文复制候选；为每个引擎校准成本，再取折中批量。

Architecture

浅轮提出候选 → 请求/循环行内打包 → 深轮批量验证 → 接受前缀，丢弃尾部；保留逐请求状态。

Key Innovation

把优化单位从 token 或整次 forward 换成读取同一份 KV 的行；对循环层级特定，比纯增大 draft length 更直接。

Experiments

论文覆盖三种 GPU（RTX 3090、4090、H100）、四个 Ouro 模型、六类评测和最高 32K 上下文；比较点内最快既有调度，并另列跨引擎实验。

Key Results · 作者报告

作者报告 164 个设置点中 161 个更快，中位 1.25×、最高 1.76×，对点内最快既有调度；作者报告 FP32 的 token 一致性，BF16 的近似并列可能出现差异。

Editorial Assessment

Why It Matters · 编辑分析

如果循环模型进入线上服务，缓存访问模式与并发负载可能比单请求 acceptance 更能预测整体收益。

Limitations

评估以 Ouro 系列为主；极高并发下提升受 KV 容量和带宽限制，不能外推到任意模型或 TP/PD 配置。PackLoop 独立仓库未核实。

Editor Note

优先复现同引擎比较，按并发和序列长度测每步读取字节；避免把跨引擎差距归因给调度。

Related Work

同面向循环深度 serving；PackLoop 改请求与循环行上的位置布局，论文另列跨引擎比较。

02 · Ouro

Ouro 给出循环语言模型及自推测场景；PackLoop 专门处理线上并发时的 KV 读取。
