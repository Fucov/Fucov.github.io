PUBLISH DATE

Submitted 2026-11-18 19:19:42 UTC · arXiv new-list date 2026-11-20 (announcement time not shown)

VENUE

arXiv:2611.25078v1 · cs.DC

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

The paper identifies the indexer cache as a new HBM bottleneck after the main KV cache is offloaded for long-context sparse attention. Twindex stores the full indexer cache in host memory and a compact shared-plus-residual copy in HBM. The compact copy selects a larger candidate set; the model's indexer then scores the original candidate rows, preserving the model's selection semantics within the candidate set.

中文摘要

长上下文稀疏注意力在卸载主 KV 后，indexer cache 仍可能占据大量 HBM。Twindex 将完整 indexer cache 放在主机内存，仅保留共享成分与压缩残差组成的 HBM 副本；先选较大的候选集合，再由模型原 indexer 对候选原始行排序。无需改权重，并可嵌入 CUDA Graph。

Technical Analysis

PROBLEM

主 KV cache 卸载并不能解决所有显存瓶颈。稀疏模型每个 decode step 都要扫描 indexer cache；在 1M context 下，论文报告其占 Qwen 每请求 HBM 的 63%、DeepSeek V4.1 的 75%。

METHOD

将 indexer cache 的共享成分与残差离线学习/编码为紧凑副本；HBM 副本执行 coarse selection，主机内存保存完整索引，再通过模型 indexer 对候选原始行完成 fine selection。

ARCHITECTURE

Host DRAM 保存 full indexer cache；GPU HBM 保存 compact copy；GPU coarse selector 产生候选行；原始 indexer 对 host-resident candidate rows 做精筛；主 KV 另在 host memory offload/prefix reuse。CUDA Graph-compatible。

KEY INNOVATION

将稀疏 attention 的 indexer cache 视为独立的容量瓶颈，并用 coarse-to-fine selection 以压缩副本减少 HBM 占用；不是简单把主 KV 再做一层 offload。

EXPERIMENTS

Qwen3.8-Flash-Next、DeepSeek V4.1-Flash、GLM-5.2；1M-token context。论文摘要称 modern GPUs，具体型号、完整负载分布与 host-memory 配置未披露。

KEY RESULTS · SOURCE-REPORTED

相对仅 offload 主 KV，1M context 可容纳请求数分别为 1.78×、1.62×、3.03×；host memory 不限制 batch 时 decode throughput 为 1.44×、1.25×、2.54×。平均 benchmark score 最多低 3.1%。这些数值对应不同模型，不能合并为单一最大加速。

Editorial Assessment

WHY IT MATTERS

指出 sparse attention serving 的显存账单不只来自 main KV；indexer state 在 KV offload 后可能成为新瓶颈。对 DSA/Indexer 类架构有直接工程意义。

LIMITATIONS

候选筛选存在近似；HBM/host-memory 互相制约；硬件与完整负载未在摘要披露；平均质量差距及各模型结果需结合正文验证。

EDITOR NOTE · ANALYSIS

值得优先阅读：它把“稀疏 attention 省 KV”后隐藏的索引状态成本明确量化，并用两级筛选维持质量。复现时重点看候选集召回、host-memory 带宽和 CUDA Graph 的实际收益。

Related Work

01

DeepSeek-V3 / sparse-indexer architecture context

共同点：同样依赖稀疏路由/indexer 选择历史位置。

核心区别：Twindex 优化 indexer cache 的存储层，而非改模型的 sparse-attention 机制。

新增量：把 indexer cache HBM residency 变成可独立压缩与 offload 的对象。

02

LMCache

共同点：将 KV/cache state 跨 GPU、CPU 与存储层管理。

核心区别：LMCache 面向 KV blocks 的通用复用；Twindex 针对 sparse-attention indexer state。

新增量：对索引器做模型结构感知的 coarse-to-fine selection。

03

PagedAttention / vLLM

共同点：优化长上下文 serving 的显存容量与碎片。

核心区别：PagedAttention 管理主 KV block；Twindex 管 indexer cache 的候选选择和驻留。

新增量：展示 main KV offload 后仍存在独立 HBM bottleneck。

PUBLISH DATE

Submitted 2026-11-18 19:29:56 UTC · arXiv new-list date 2026-11-20 (announcement time not shown)

VENUE

arXiv:2611.25091v1 · cs.DC

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

Berth controls what the best-effort context is allowed to submit rather than modifying the GPU kernel, driver or framework. A preloaded user-space shim feeds best-effort work only when latency-sensitive requests do not need the GPU. A deadline reference extends this control to continuous-batching LLM engines, and a shorter time slice bounds long best-effort kernels.

中文摘要

推理服务常按峰值预留 GPU，闲置容量难以安全共享。Berth 不修改应用、框架、kernel 或 driver，而在用户态控制 best-effort job 何时提交 GPU 工作，并用 deadline reference 适配 continuous batching；缩短 best-effort time slice 限制长 kernel 的影响。

Technical Analysis

PROBLEM

Spatial sharing 无法抢走正在运行的 kernel；temporal sharing 让请求等待；MIG 等 partition 可能闲置资源。闭源 GPU stack 的 operator 难以修改 kernel/driver 来建立优先级。

METHOD

预加载 shim 控制 best-effort feed；服务请求到达时停止提交 best-effort 工作；声明 deadline reference 让控制规则适配连续批处理；设置较短 best-effort time slice，限制一次干扰时间。

ARCHITECTURE

Latency-sensitive context + best-effort context；user-space shim / feed-control；GPU 现有 time-slicer；continuous-batching deadline reference；best-effort time-slice 参数。无需改 driver/kernel/framework。

KEY INNOVATION

将“优先级”转化为外部 feed-control：不创建新 preemption，而利用 GPU 已有上下文切换与 time-slicing 机制，让 best-effort context 在没有 serving 请求时才有工作可执行。

EXPERIMENTS

31 个 scenario points、13 个 baseline，采用 MLPerf SLO；另与 continuous-batching LLM serving + training 共置。摘要未披露完整 GPU 型号、每个 workload 的规模与时间片参数。

KEY RESULTS · SOURCE-REPORTED

SLO 距离单独运行仅几个百分点，优于所有比较 baseline；best-effort throughput 为最强 baseline 的 2.7–3.5×。LLM serving 场景中几乎所有 request 都满足 per-token target，同时 training 持续运行。

Editorial Assessment

WHY IT MATTERS

为闭源/托管 GPU stack 提供低侵入 GPU sharing 路径，适用于 inference 与 best-effort training 共置。

LIMITATIONS

对 GPU time-slicer 行为与 feed-control 的假设依赖较强；完整硬件、 workload 和尾延迟分布未披露；best-effort time slice 变短可能影响其自身效率。

EDITOR NOTE · ANALYSIS

研究问题切得很准：不用新增抢占能力，只控制提交队列。但要复现，需要检查 time-slicer 的真实粒度、GPU 型号、driver 版本及 request arrival pattern，不能仅凭摘要的 SLO 结果判断跨平台可移植性。

Related Work

01

NVIDIA GPU time-slicing

共同点：利用 GPU context 时间片共享。

核心区别：Berth 在 user-space 进一步控制 best-effort feed 与时片长度，而非仅配置共享。

新增量：把现有时间片机制变成可按 serving deadline 保护的调度控制。

02

NVIDIA MIG

共同点：为 GPU workload 隔离资源。

核心区别：MIG 空间分区，可能为保护 SLO 留下未用资源；Berth 共享时间片。

新增量：在不硬分割 GPU 的情况下填补 serving 空闲窗口。

03

CUDA Multi-Process Service (MPS)

共同点：允许多个进程并发使用 GPU。

核心区别：MPS 侧重并发与资源配额，Berth 针对 deadline/SLO 的 best-effort 提交控制。

新增量：以外部提交控制建立 latency-sensitive 与 best-effort 的优先关系。

PUBLISH DATE

Submitted 2026-11-18 19:50:23 UTC · arXiv new-list date 2026-11-20 (announcement time not shown)

VENUE

arXiv:2611.25112v1 · cs.DC / cs.AR / cs.OS

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

TripleKV manages agent KV state across GPU, host DRAM and SSD. During tool execution, the next KV blocks are known but their reuse time is uncertain. A tool-aware latency predictor prefetches them from SSD to DRAM; duplicate DRAM copies of GPU-resident blocks are removed and a victim cache refills blocks after GPU eviction.

中文摘要

Agent 在 inference 与 tool execution 间切换，KV 工作集可能达到数百 GiB。TripleKV 预测 tool call 完成时间，在等待期间将下一轮需要的 block 从 SSD 预取到 DRAM，避免抢占 GPU memory；同时去重 DRAM 中 GPU-resident blocks，并用 victim cache 处理 GPU eviction。

Technical Analysis

PROBLEM

Agent 返回模型时，若 KV blocks 已从 GPU/DRAM eviction 到 SSD，SSD read 会进入 TTFT critical path。Tool execution 提供可利用的 idle window，但 tool completion time 不确定。

METHOD

Tool-aware latency predictor 预测 tool call completion；在 GPU memory 不预留的情况下 SSD→DRAM prefetch；去重 GPU-resident blocks 的 DRAM copies；GPU eviction 时由 victim cache 从 SSD refill。

ARCHITECTURE

GPU KV cache ↔ DRAM tier ↔ SSD tier；tool executor latency predictor；prefetch scheduler；DRAM deduplication；victim cache。预取窗口由 tool execution 提供。

KEY INNOVATION

把 Agent tool-execution 的等待时间变成 cache prefetch window；只需知道下一次要复用哪些 blocks，不必精准预测何时返回。

EXPERIMENTS

Data、web、coding agents；高并发工作集可达数百 GiB。硬件、模型与具体 trace 规模未披露。

KEY RESULTS · SOURCE-REPORTED

Critical-path SSD read 的 request fraction 从 45–76% 降至 <10%；相对 vLLM + DRAM/SSD KV tiers，P95 TTFT 最多降低49%；相对 recent agent-aware systems，P95 TTFT 低1.5–7×。

Editorial Assessment

WHY IT MATTERS

把 tool-call latency 与 tiered cache management 联动，避免传统 prefetch 占用 GPU memory，尤其适合长状态 Agent serving。

LIMITATIONS

依赖 tool-call duration predictor 与工作集可预知性；数据集/硬件/模型规模未披露；prefetch 错误或工具耗时分布变化可能导致 cache pollution。

EDITOR NOTE · ANALYSIS

与单纯扩展 KV tier 相比，关键是预测“何时回来”。值得重点看 latency predictor 的 calibration、prefetch miss 与 victim-cache 机制是否在真实 tool latency traces 下稳健。

Related Work

01

SGLang HiCache

共同点：GPU/host memory 的分层 KV cache。

核心区别：HiCache 提供层次 cache；TripleKV 将 tool-call latency 纳入 SSD→DRAM prefetch timing。

新增量：以 agent tool execution 隐藏 cache retrieval。

02

LMCache

共同点：跨 GPU、CPU、storage tier 的 KV reuse。

核心区别：LMCache 是通用 cache layer；TripleKV 聚焦 agentic block reuse timing 与 dedup/victim cache。

新增量：为下一轮已知 KV block 做 tool-aware prefetch。

03

CacheBlend

共同点：利用 cache reuse 减少重复 prefill。

核心区别：CacheBlend 面向 non-prefix KV reuse；TripleKV 面向跨 Agent turn 的 tiered cache retrieval。

新增量：将 SSD retrieval 从 critical path 转移至 tool wait。

VENUE

arXiv:2611.26106v1 · cs.DC

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

FP4 KV cache compression requires block scaling, but MLA shares latent representations whose K and V paths have different scaling requirements. AscMLA combines asymmetric K/V scaling with pipelined scale delivery so a single FP4 payload can be used directly without dequantization or separate encodings.

中文摘要

MLA 的 shared latent 同时服务 K/V，但两条路径的 scaling requirements 不同。AscMLA 使用 asymmetric K/V scaling，并将 scale delivery pipeline 化，以单份 FP4 payload 直接执行，减少解码过程中的额外存储与计算。

Technical Analysis

PROBLEM

FP4 的动态范围较小，需要 block scaling；MLA shared latent 中 K/V scale 不同，传统解量化或双编码增加运行时/存储 overhead。

METHOD

Asymmetric K/V scaling + pipelined scale delivery，使用一个 FP4 payload，避免额外 dequantization 或 separate encodings。

ARCHITECTURE

MLA latent cache → FP4 payload；K/V asymmetric scale metadata；scale pipeline 与 decode kernel overlap；直接读取 FP4 payload。

KEY INNOVATION

把 K/V scaling 不对称作为 MLA FP4 cache 的设计核心，并将 metadata delivery pipeline 化。

EXPERIMENTS

Long-context MLA decoding；与 TensorRT-LLM FP8 与 CAKE NVFP4 MLA kernels 对比。GPU 型号、模型、context lengths 未披露于摘要。

KEY RESULTS · SOURCE-REPORTED

KV cache memory 比 FP8 少38.2%；geometric mean speedup 1.35× vs TRT-LLM FP8，1.26× vs CAKE NVFP4 MLA kernels。

Editorial Assessment

WHY IT MATTERS

低精度 KV 不只是格式转换：共享 latent 的 K/V 数值结构与 scale metadata delivery 会决定 decode kernel 能否真正省带宽。

LIMITATIONS

硬件与模型/上下文配置未披露；质量/精度影响需看正文；FP4 kernel gains 可能受 memory bandwidth、batch 与 scale overhead 影响。

EDITOR NOTE · ANALYSIS

值得看 kernel mapping 与 scale pipeline 是否真的 overlap；摘要给出相对性能，但缺少硬件、context length 与 accuracy envelope，暂不应把结果外推到所有 MLA 模型。

核心区别：NVFP4-MLA 联合 cache 与计算；AscMLA 聚焦 shared latent 的 asymmetric scale 和 scale delivery。

新增量：单 payload 的 K/V 直接执行，降低 FP4 cache 的额外操作。

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

KernelOPT profiles compiler-generated kernels and external library calls, then uses specialized agents to plan and implement targeted transformations. It assembles optimized kernels back into models and validates them through static checks, multi-seed numerical comparisons, model-level checks, and an end-to-end performance gate. The v3 revision adds a public implementation and broader benchmark results.

中文摘要

KernelOPT 以 NCU metrics 驱动 Planner/Executor 等 agents，识别 memory/compute/launch bottleneck，生成 targeted transformations；识别 Inductor dispatch 到 cuBLAS/cuDNN 的调用并保留，避免盲目替换；经过 static、multi-seed correctness、float64、model-level 与 end-to-end performance gates，未达门槛时 fallback。

Technical Analysis

PROBLEM

LLM kernel optimization 容易获得 isolated kernel speedup，却在 model-level dispatch、融合与库调用中产生 regression；优化器缺少 hardware profiling 和 E2E validation。

METHOD

NCU profiling → bottleneck classification → planner/executor agents → search/beam selection → correctness gates → E2E performance gate；dispatch-aware 保留外部库 calls。

ARCHITECTURE

Profiler/Planner/Executor/Correctness/Summarizer agents；multi-kernel pipeline；beam/greedy/top-k/UCB search；torch.compile/Inductor kernel extraction；safe fallback。

KEY INNOVATION

将 dispatch context、profiling evidence 与 model-level acceptance 组合进 agentic kernel search，优化目标从 kernel isolated time 转向端到端模型。

EXPERIMENTS

250 KernelBench problems on NVIDIA H200, FP32, torch.compile baseline；L1 100 single-op、L2 100 composite、L3 50 architectures；另 10 Triton + 10 Helion tutorial kernels。

KEY RESULTS · SOURCE-REPORTED

Geomean across all kernels: L1 1.40×, L2 1.15×, L3 1.07×；optimized-only geomean 2.54×/1.84×/1.37×；250 kernels 0 regressions，未提升则 fallback。v3 code publicly available。

Editorial Assessment

WHY IT MATTERS

提供较可复现的 agentic kernel optimization stack，并强调 compiler dispatch 与 model-level performance gating；适合系统研究 kernel agents 的实验基线。

LIMITATIONS

KernelBench synthetic/curated workload；FP32；收益含 tolerance 下的 precision/algebra changes；agent inference cost、真实模型与跨硬件泛化需进一步验证。

EDITOR NOTE · ANALYSIS

v3 是实质性更新：公开实现、250-kernel evaluation、zero-regression fallback。对 kernel-agent 研究有价值，但优化-only geomean 与全 benchmark geomean 必须分开看。

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

The v3 revision evaluates a hierarchy spanning HBM, high-bandwidth flash, and host memory for agentic LLM serving. 中文摘要

Technical Analysis

PROBLEM

仅 HBM 容量有限；HBF 容量更大但读写成本与 endurance 可能限制 serving。Cache placement 和 scheduling 需同时考虑 throughput、energy 与写寿命。

METHOD

HBM-HBF-host hierarchical storage；buffered cache-aware scheduling；trace-driven simulations，评估 weight/KV placement 与 workload。

ARCHITECTURE

HBM hot tier → HBF capacity tier → host tier；buffering 与 cache-aware scheduler 控制数据 placement、读写和 endurance。

KEY INNOVATION

把 HBF 作为 actively utilized serving memory tier，而非 passive storage，并联合 placement/scheduling/energy/endurance。

EXPERIMENTS

Trace-driven simulation；agentic serving workloads；硬件 HBF 设备与具体 trace details 未披露。v3 更新结果，不能把 v2 数字当当前版本。

KEY RESULTS · SOURCE-REPORTED

v3：completion time 相对 HBM-only 降21.1–86.9%；modelled energy savings 最高62.4%；buffered scheduling 估计 HBF lifetime 从0.99延至13.63年（指定配置）。

Editorial Assessment

WHY IT MATTERS

为 agentic serving 的 memory hierarchy 与 storage endurance 提供 system-level design space，强调容量扩展需与调度共同设计。

LIMITATIONS

模拟结果而非真实 HBF hardware deployment；completion-time 范围强依赖 workload、placement；energy/lifetime 为 modeled estimates；v3 与 v2 指标发生变化。

EDITOR NOTE · ANALYSIS

Abstract

ORIGINAL ABSTRACT SUMMARY · EN

TRANSIT uses CPU DRAM as an extension of GPU memory during distributed LLM training. A user-space interposition layer coordinates driver-managed page residency and execution-guided zero-copy access to exploit recurring kernel patterns, requiring no changes to application, framework, scheduler, driver, or OS.

中文摘要

LLM training state 占显存迫使作业扩展到更多节点，增加通信与排队。TRANSIT 以 user-space interposition layer 协调 driver-managed page residency 与 execution-guided zero-copy，利用 kernel iteration 的重复模式将 CPU DRAM 作为 GPU memory extension，实现 transparent scale-in。

Technical Analysis

PROBLEM

Training state capacity 决定 GPU 数量；多节点增加通信并降低 per-GPU efficiency。传统 framework-managed offload 与 driver-runtime oversubscription overhead 较高。

METHOD

User-space interposition；协调 driver-managed page residency；execution-guided zero-copy CPU-GPU access；利用 recurring kernel execution patterns。

ARCHITECTURE

Training application/framework unchanged；user-space interposition；GPU page residency / CPU DRAM extension；execution-guided data movement；RoCE multi-node。

KEY INNOVATION

将 transparent memory oversubscription 与 execution-guided zero-copy data path结合，使 scale-in 不需要修改 training framework/driver。

EXPERIMENTS

Dense 与 MoE models、多种 parallelism；最多64× NVIDIA H100-80GB，RoCE。v2 revision 更新结果与摘要。

KEY RESULTS · SOURCE-REPORTED

最多50% fewer GPUs，保留 baseline >90% per-GPU compute throughput；比 driver-runtime oversubscription throughput 高最多243%，比 framework CPU offload 高87%；CPU memory consumption 少79%；network traffic 少33%；受限网络 throughput 提升44%。Trace-driven simulation inter-rack traffic 少15–49%，queue time 减少2–95%（不同 capacity）。

Editorial Assessment

WHY IT MATTERS

从 GPU memory oversubscription 角度减少训练资源 footprint，特别适合 queueing/communication bottleneck 下 scale-in。

LIMITATIONS

依赖 page-residency、zero-copy path 与重复 kernel pattern；只验证 H100/RoCE；simulation queue-time results 不等于 production deployment；v2 与 v1 metrics changed。

EDITOR NOTE · ANALYSIS

这是 major revision 重收：v2 title/abstract/results 改为 transparent scale-in 与 execution-guided zero-copy，并扩展数据。复现时要区分 GPU throughput、network traffic 与 trace-driven queueing simulation。
