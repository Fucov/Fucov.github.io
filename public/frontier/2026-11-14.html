Publish Date

merged 2026-11-14 12:38:18 UTC / 20:38:18 Asia/Shanghai

Venue

vLLM core code · PR #64753 · commit e72e9cb18b42

Abstract

Original Abstract Summary

This vLLM change keeps CSF-compressed NVFP4 routed-expert block scales resident on the GPU for the B12X backend. At load time each rank re-encodes its scale slice; at execution time B12X expands only the routed experts into a shared scratch buffer, trading modest inter-token latency for lower model memory and larger KV capacity.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

针对 Qwen3.8-Flash-Next-FP4-Local，B12X 后端将 routed-expert scales 以 CsfScalePlanes 保持压缩；每层调用只展开本次 top-k 专家到按层形状共享的 scratch。该路径仅对 NVFP4 activation 与 csf checkpoint 默认启用，并提供回退开关。

Technical Analysis

Problem

加载时解压所有专家尺度会占用数 GiB HBM，直接挤压 KV cache；本地/消费级 GPU 上容量往往比算力更先成为限制。

Method

用 FlashInfer encode_csf_scales 重编码每个 TP rank 的 decoded slice；B12X execution 按路由专家动态展开尺度，scratch 按 layer shape 共享；CUDA Graph replay 和 TP1/2/4 做一致性测试。

Architecture

Checkpoint CSF scales → rank-local decode/re-encode → resident CsfScalePlanes → routed expert IDs → per-call selective expansion → shared scale scratch → B12X NVFP4 MoE kernel。

Key Innovation

将量化元数据也视为可按稀疏路由调度的工作集，而不是默认完整驻留；容量收益来自 expert sparsity，而非降低权重精度本身。

Experiments

Qwen3.8-Flash-Next-FP4-Local、MTP-3、B12X；DGX Spark GB10 与 RTX PRO 6000 Max-Q 300W。随机服务输入 1024、输出 256，concurrency 1/4/8；GSM8K-256 5-shot；48 个 kernel 测试。

Editorial Assessment

Why It Matters

MoE 低精度模型的量化尺度并非“免费元数据”。把 scales 与路由稀疏性共同管理，可把节省空间直接转化为 KV 容量。

Limitations

仅支持 B12X、TP-only、NVFP4 activations 与 csf encoding；不支持 expert parallelism 和 compressed layer weight reload。容量换来高并发 ITL 回退，且部分数字沿用早期 in-tree encoder 测量。

Editor Note

S 级。容量收益、延迟代价与正确性均被量化，取舍披露透明；适用硬件和 backend 范围较窄。

Related Work

共同点是压缩尺度常驻；该后续路径面向 MXFP4 W4A8，本作面向 NVFP4 W4A4/csf checkpoint。

02
FlashInfer B12X / CSF

共同点是 compact scale planes 与 inline/动态展开；vLLM 新增 checkpoint、TP、CUDA Graph 和 serving 生命周期接入。

共同点是降低模型内存；本作进一步压缩 block-scale metadata，并利用路由稀疏性按需展开。

SGLang open-source project；具体机构未披露

Publish Date

merged 2026-11-14 10:21:34 UTC / 18:21:34 Asia/Shanghai

Venue

SGLang core code · PR #46363 · commit 19af0c78a2e8

Abstract

Original Abstract Summary

SGLang changes HiCache pipeline-parallel synchronization from a single-round drain to a bounded per-round send window sized as pipeline size plus asynchronous batch depth. Because Gloo sends complete only after the receiver posts a matching receive, the old drain serialized neighboring ranks; the new window preserves FIFO semantics while allowing bounded run-ahead.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

旧实现每次 check_hicache_events 开始都等待上一轮全部 isend，导致 rank r 的第 k+1 轮必须等 rank r+1 进入第 k 轮 HiCache 步骤，抵消 pp_async_batch_depth。新实现按轮保存 Work deque，仅在 outstanding 轮数超过 pp_size+depth 时等待最老轮。

Technical Analysis

Problem

HiCache 的 PP sync channel 在有 runnable work 时仍形成邻接 rank 锁步；报告场景 PP8 prefill 中 PP0 约 20% loop 时间卡在等待。简单不回收又会重现 Work 列表泄漏。

Method

以轮为单位记录异步 send；窗口等于 PP loop_size，FIFO tag 保持消息次序；超过窗口只等待最老轮。参数经 CacheInitParams 显式传入，避免 cache 构造依赖全局 runtime context。

Architecture

Each PP rank: scheduler round → HiCache sync isend → work_rounds deque → bounded oldest-round wait；next rank 在自身 HiCache step 依序 recv，窗口与 pp_size + pp_async_batch_depth 对齐。

Key Innovation

把控制通道背压上界与执行流水本身的可前跑深度统一，既避免 Gloo 的隐式 rendezvous 串行化，也保持有界资源。

Experiments

CPU 4-rank Gloo 模型；硬件 2×B200、Qwen3-1.7B、PP2×TP1、HiCache write-through、chunked prefill 4096、600 个渐进请求加 3×400 burst；另有 fixed prompts 正确性。

Editorial Assessment

Why It Matters

层次 KV cache 一旦进入 PP serving，控制消息也会成为调度关键路径。该修复说明“异步 batch depth”必须贯穿 cache control channel 才有真实含义。

Limitations

未在原报告的 PP8 Kimi-K3、两节点 GB300 规模复现；一个 rank 永不 post recv 时仍会最终停顿；当前硬件案例主要验证机制而非端到端吞吐。

Editor Note

A+。机制、边界和负面结果披露充分；对大规模目标 workload 的收益尚待复现。

Related Work

01
SGLang HiCache

共同点是 GPU/host/external KV 层次；本作只改变 PP 控制通道的背压与前跑语义。

02
Pipeline parallel async schedules

共同点是允许 rank/stage 前跑；本作让 cache-sync side channel 服从同一深度，而非暗中锁步。

03
Credit-based flow control

共同点是有界 outstanding window；这里 credit 直接取执行 pipeline loop_size，并利用 FIFO Gloo tag。

TensorRT-LLM：加速 CUTLASS MoE 行展开与激活启动

利用 permuted rows 已按 expert 排序的性质，把 FP8 block-scale 行展开从“每行二分 expert offset”改成“每 block 一次搜索后线性推进”，并让激活 block 宽度匹配 TP 后的窄行。

NVIDIA / TensorRT-LLM

Publish Date

merged 2026-11-14 08:09:02 UTC / 16:09:02 Asia/Shanghai

Venue

TensorRT-LLM core code · PR #21178 · commit 6808cedaa7ac

Abstract

Original Abstract Summary

TensorRT-LLM optimizes two shared CUTLASS MoE stages. Row expansion searches expert offsets once per contiguous block and advances linearly across sorted rows. The activation launcher selects whole-warp block widths based on the per-rank row width, reducing idle threads for tensor-parallel narrow intermediate slices across FP8, NVFP4, MXFP8, W4A16, and related CUTLASS paths.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

改动一是利用路由后行按 expert 排序，避免每个 permuted row 重复二分 offset；二是把固定 256-thread 激活 block 改成与行宽匹配的整 warp 数，避免 TP4/TP8 将 intermediate 切窄后大量线程空闲，同时把 occupancy cache key 扩展到 block size。

Technical Analysis

Problem

MoE 路由后的 row expansion 和 activation 虽不是 GEMM 主体，但在长 prefill 或窄 TP shard 下累积明显；固定 block 宽度使 512-wide slice 约四分之三线程空闲。

Method

每 CUDA block 处理连续 permuted rows，首次二分后按 expert offset 线性走；activation 根据每行 column vectors 选择 warp-aligned block size；occupancy cache 按 kernel、block 和动态 shared memory 区分。

Architecture

Routing/permutation → expert-sorted rows → block-local offset walk → CUTLASS grouped MoE → width-aware activation/quantization launch；适用于 SM80–SM120 多量化路径。

Key Innovation

不是替换核心 GEMM，而是系统性缩减 MoE 前后处理的搜索与空线程固定开销，并让同一 launcher 对 TP 形状自适应。

Experiments

GLM-5.3-Flash FP8，H200 TP4、MTP3、BF16 KV，ISL 1K/4K/13K；另测 B300 上 DeepSeek-R1 单层 NVFP4，256 experts、top-8、hidden 7168，intermediate/rank 256/512/2048、tokens 1–8192。

Editorial Assessment

Why It Matters

随着 GEMM 越来越快，permutation、scale expansion 和 activation launch 成为剩余 Amdahl 瓶颈；该改动覆盖多个量化后端且有端到端 TTFT 证据。

Limitations

端到端提升主要出现在长 prefill、C1 和窄 TP shard；decode/C8 在噪声内。部分 kernel 数据来自开发分支，不能外推到所有 CUTLASS MoE 配置。

Editor Note

A+。工程新增量清晰，跨 FP8/NVFP4 提供微核与端到端结果；方法更多是高质量实现优化而非新算法。

SM107 MXFP8 Autotuning Across CUTLASS, CuTe-DSL and cuDNN

FlashInfer：在 SM107 上联合选择 CUTLASS、CuTe-DSL 与 cuDNN 的 MXFP8 GEMM

Publish Date

merged 2026-11-13 17:51:34 UTC / 2026-11-14 01:51:34 Asia/Shanghai

Venue

FlashInfer core code · PR #9020 · commit 88077bda83a7

Abstract

Original Abstract Summary

FlashInfer expands the SM107 MXFP8 GEMM autotuner candidate set from CUTLASS alone to suitable CUTLASS, CuTe-DSL, and cuDNN tactics. All candidates use the same CUDA-graph cold-L2 measurement configuration, while unsupported cuDNN graphs decline gracefully instead of aborting tuning. Other architectures retain the prior CUTLASS-only policy.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

此前 SM107 的 auto 路径只返回 CUTLASS，使用者必须手工指定 CuTe-DSL，且无法同时比较 cuDNN。新路径按输入适用性收集三个 backend，在同一 profiling 配置下排序；若 cuDNN graph 不支持则返回无 tactic，而不是让整个 auto tuning 失败。

Technical Analysis

Problem

DeepSeek-V4.1 大 prefill 的某些 MXFP8 GEMM 形状由 cuDNN 2-CTA/B-reuse tactic 更快，但默认 auto 永远不会测到；手工路由难以随形状和硬件维护。

Method

SM107-only candidate expansion；统一 CuTe-DSL tuning config；cuDNN get_valid_tactics 对不支持 graph 安全降级；winner 缓存保持现有 runner 语义。

Architecture

mm_mxfp8(auto) → suitability filters → CUTLASS/CuTe-DSL/cuDNN tactic runners → CUDA Graph + cold-L2 profiling → per-shape cached winner；非 SM107 保持原策略。

Key Innovation

把 backend 选择从静态 heuristic 升为架构与形状条件下的同口径竞争，并明确限制到测得收益的 SM107，避免跨架构盲目扩张。

Experiments

单张 SM107；DeepSeek-V4.1 dense MXFP8 GEMM 形状，CUDA Graph 10 calls；另在 B300 双卡做负面对照。SGLang 16K tokens/GPU prefill 做端到端 hand-routing 验证。

Editorial Assessment

Why It Matters

低精度 kernel 生态已不是单一实现胜出；对具体 GPU/shape 自动选择比硬编码 backend 更能吸收 CuTe-DSL 与库内核的快速演进。

Limitations

收益限定 SM107 和大 prefill；端到端自动选择后的完整服务数字未披露，且首次 tuning 成本显著。缓存 shadowing 可能让旧 CuTe-DSL winner 阻止 cuDNN 被重新测量。

Editor Note

A+。正负结果和调优成本披露完整，范围控制克制；端到端收益仅 1.1%，主要价值是可维护性与自动决策。

Publish Date

merged 2026-11-14 09:44:43 UTC / 17:44:43 Asia/Shanghai

Venue

SGLang core code · PR #50324 · commit 50106ca2d768

Abstract

Original Abstract Summary

SGLang extends its direct external cache linker to MXFP8 KV caches. The device-pool page representation now packs K/V UE8M0 scale buffers after the FP8 payload, preserving aligned whole-page transfers for both interleaved and flat layouts. A long-context Inkling test validates restored log-probabilities against cold-prefill replay.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

此前 --kv-cache-dtype mxfp8 与 unified cache external linker 组合会因 scale buffer 被拒绝而启动失败。新实现将 K/V scale buffers 视为 KV page 的必要组成部分，按 uint8 aligned rows 附加在 payload 后面，通过 Mooncake/RDMA 整页搬运；FP4 scaled KV 仍拒绝。

Technical Analysis

Problem

低精度 KV 不只有 payload，还依赖 per-block scales。若 linker 只搬 FP8 数据或直接拒绝 scale pool，分层缓存无法用于 MXFP8 长上下文 recipe。

Method

扩展 device pool assembler，把 interleaved page_size=128 与 flat layout 的 UE8M0 scale rows 打包入同一 page object；保持既有 pool key，不创建额外存储命名。

Architecture

GPU MXFP8 K/V payload + UE8M0 K/V scales → assembled aligned KV page → direct external linker → Mooncake RDMA/L3 → restored GPU page → attention decode。

Key Innovation

把量化元数据纳入 cache page 的原子传输语义，使分层 KV cache 与 MXFP8 不再是互斥功能。

Experiments

Inkling test revision、1×B200、FA4、page size 128、deterministic inference、Mooncake over RDMA。每个第二轮把完整 prefix 从 L3 restore，并用 filler 覆盖释放过的设备页；对照 cold prefill replay 的 decode logprobs。

Editorial Assessment

Why It Matters

Abstract

Original Abstract Summary

This merged vLLM change replaces per-tensor sparse NCCL patch broadcasts with bounded, dtype-grouped batches. Workers apply each batch before receiving the next, reducing staging memory, allocation count, broadcast count, and empty-cache overhead while preserving update ordering and recoverability after validation failures.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

该合入针对在线 RL 中 trainer 向推理侧发送稀疏权重补丁的 OOM 与高固定开销：补丁按元数据确定性分批，索引和同 dtype 数值分别拼接广播；worker 复用接收缓冲并切成视图，完成一批即写入权重，避免整次更新同时驻留 GPU。

Technical Analysis

Problem

原实现让每个 rank 暂存全部补丁，且每个 tensor 产生两次分配、两次 broadcast。Qwen3-30B-A3B TP4 在默认约 3 GiB 空闲显存下，更新 1.25% 元素即 OOM；37,734 次 broadcast 也放大延迟。

Method

按补丁元数据切分不超过 512 MiB 的批次；trainer 将非连续 patch 拼接成连续 wire buffer；worker 每批接收、校验、切视图并立即应用，失败时仍排空后续广播后统一抛错。

Architecture

Trainer patch metadata → deterministic batch partition → indices/value buffers per dtype → NCCL broadcast → worker shared receive buffer → per-patch views → in-place weight update；控制面保持 pause/resume 与错误归集。

Key Innovation

把稀疏增量同步的显存复杂度从总更新量 O(update) 降为 O(batch_limit)，同时将通信调用从“按 tensor”折叠为“按批次与 dtype”。

Experiments

4×H20 TP4 serving + 第 5 张 H20 trainer；Qwen3-30B-A3B、Triton MoE、torch 2.14.0+cu130。更新密度 0.1%–50%；另测 32 个流式客户端，以及 Qwen3.5-35B-A3B。

Editorial Assessment

Why It Matters

在线 RL 的 rollout 引擎需要频繁接收新 policy；如果同步本身会 OOM、阻塞 NCCL 或暂停数秒，actor–learner 解耦就失去意义。该改动把同步路径变成可扩展的数据面。

Limitations

结果来自两类 Qwen MoE 和 H20 TP4；极大 50% 更新虽能完成，但并不代表稀疏协议在该密度下优于全量同步。补丁分批后仍非事务性原子更新，失败期间 worker 可能已写入前序批次。

Editor Note

S 级。问题直接命中 RL serving 的显存与控制面可靠性，实验披露硬件、密度、延迟和正确性；但仍是框架内部协议，跨后端复现有限。

PyTorch / TorchTitan open-source project；具体机构未披露

Publish Date

PR #5996 merged 2026-11-14 07:55 Asia/Shanghai；#5997 merged 10:07 Asia/Shanghai

Venue

TorchTitan core code · PR #5996 + #5997

Abstract

Original Abstract Summary

TorchTitan adds a model-state transport built on torch.distributed._transport and wires it into the RL loop behind an opt-in flag. Trainer ranks register aligned pinned staging buffers; generator ranks plan one-sided Mooncake or NIXL reads that cover their target shards, including layout transforms between FSDP/HSDP and tensor-parallel placements.

Faithful English summary of the official PR description; not a verbatim abstract.

中文摘要

新路径去掉 TorchStore 中转，让 generator 按自身 shard layout 从各 trainer rank 的 pinned CPU staging buffer 直接拉取。若 trainer shard 与 generator shard 的维度切分不匹配，stage 阶段先用一次 redistribute 把后续维度 shard 移到首个分片维度，再生成连续 RDMA read 计划。

Technical Analysis

Problem

TorchStore 为 RL 模型同步引入额外 store、controller 和拷贝；14B 单机 8×B200 下 generator pull 需要 10–13 s，远慢于 RDMA 可用带宽。布局差异又使“直接读 trainer shard”并非简单 memcpy。

Method

每 trainer rank 注册 16 B 对齐的 pinned staging buffer；按 generator rank 求 shard box 交集并去重复制；用 torch.distributed._transport 连接 Mooncake/NIXL，generator 预规划分段 one-sided reads，并用超时避免永久挂起。

Architecture

Trainer FSDP/HSDP shards → optional redistribute/restage → dtype cast + D2H pinned staging → registered transport endpoints → generator per-rank read plan → CPU prefetch buffers → model load；controller 在 push/read 阶段协调代际。

Key Innovation

把分片布局转换、registered-memory 生命周期和后端可替换的单边读取合成 PyTorch 原生 RL 同步抽象，并预留 delta/LoRA 子集同步。

Experiments

单机 8×B200 183 GiB；14B 模型；trainer FSDP4、generator TP2，NIXL；单元测试 19 个 CPU case 覆盖 HSDP 3×4→TP1/2、两种分片维度、bf16 cast、覆盖检查与超时。

Editorial Assessment

Why It Matters

权重同步是异步/共置 RL 的阶段边界。把同步从控制面 store 迁移到 registered-memory 数据面，能显著缩短 rollout policy staleness 窗口。

Limitations

依赖较新的 PyTorch nightly 与特定 Mooncake/NIXL 版本；当前是 opt-in，失败后要求重启作业；不支持 Partial 或 uneven StridedShard，跨节点和大规模多 generator 结果未披露。

Editor Note

S 级。布局语义、内存注册和一侧通信的系统设计完整，实测提升大；依赖 nightly 与有限规模使复现成本偏高。
