Abstract

Original Abstract Summary

SGLang v0.5.22 consolidates 950 pull requests from 245 contributors. The stable release expands disaggregated prefill/decode serving, speculative decoding, CPU-backed KV operation, model loading, communication and kernels across NVIDIA, AMD, Intel and Apple platforms, while adding model support and a correctness fix for hybrid recurrent state under speculation.

中文摘要

这是一次以系统整合为核心的稳定发布：PD 服务、长上下文 KV、DFlash/DSpark/EAGLE/MTP、MoE kernel 与多硬件后端被放进同一运行时，同时修补混合线性模型在投机解码与结构化输出并用时可能恢复错误状态的问题。

Technical Analysis

Problem

高吞吐 serving 的瓶颈分散在加载、P/D 调度、KV 层级、投机验证、MoE 通信与硬件适配；分别优化会造成组合不可用或 correctness 风险。

Method

以统一 scheduler/runtime 接入 InstantTensor、PD 路径、HiSparse CPU KV、DFlash/DSpark/EAGLE/MTP、DCP 与多种 MoE/kernels，并为关键模型设置后端选择与 CUDA Graph 路径。

Architecture

API 与调度层组织 prefill/decode 及 session 状态；KV 可驻留 GPU 或经 HiSparse 在 CPU 层级多步换入换出；draft/verify 路径共享图捕获与状态提交；底层按 GPU/CPU 平台选择 FlashInfer、TRTLLM、MegaMoE、DSpark/DFlash 等执行后端。

Key Innovation

新增量不是单点算法，而是把跨层级 KV、PD、speculation、MoE 与 loader 变成稳定 release 中可组合、可升级的能力，并披露多个真实模型的端到端结果。

Experiments

官方 release 汇总多项 PR benchmark：DeepSeek‑V4.1/H200、Qwen3.8‑Flash‑Next/B200、GLM‑5.3‑Flash/B300、MiMo‑V2.6‑Pro/B300，以及长 prompt PD 工作负载；未提供覆盖全部特性的统一矩阵。

Editorial Assessment

Why It Matters

SGLang 是重要开源 serving runtime，稳定版本会直接影响生产升级、容量规划和多硬件部署；PD 与 CPU-KV 路径尤其对应长上下文和 agent workload。

Limitations

最大提升依赖特定模型、GPU 与配置；950 PR 的聚合发布难以由单一实验复现。Python 最低版本提升到 3.11，升级还需验证兼容性。

Editor Note

96/S+。证据来自稳定 release 与公开代码，系统影响和可复现性极强；因性能数据分散于不同 PR、缺少统一对照矩阵扣分。

Abstract

Original Abstract Summary

The paper characterizes more than 121 million model calls from four production Microsoft M365 workloads. It measures session structure, context growth, prefix reuse, KV lifetime and placement locality, then uses trace-driven replay to compare idle caps, eviction and multi-resolution retention under constrained memory budgets.

中文摘要

论文不提出完整 serving 系统，而是给出生产轨迹层面的容量下界与策略证据：agent 会话的 KV 大量时间处于闲置但仍需保留，单纯延长 HBM 常驻不可行；压缩、迁移、路由和多级存储需要联合设计。

Technical Analysis

Problem

Agent 的多轮工具调用不断增长上下文，KV 复用价值高，但 fleet 级峰值容量、空闲寿命和跨 deployment 命中损失缺少真实规模数据。

Method

对 Deep Research、Enterprise Assistant、Coding Agent 与 Enterprise Chat 四类生产轨迹做统计，以公开 Llama‑2‑70B KV 布局统一估算容量，并进行预算约束下的 trace replay。

Architecture

分析模型把 session、call、context prefix、deployment placement 与 KV representation 分层；策略包括 idle cap、LRU/clairvoyant eviction 以及把冷 KV 降为 int4 的 multi-resolution retention。

Key Innovation

首次以超大生产轨迹把 agentic KV 的“容量—空闲—重算—placement”耦合量化，并显示表示降级比纯 eviction 更有效。

Experiments

四类 M365 workload 共超过 1.21 亿次模型调用；模型本身保密，容量按 Llama‑2‑70B、GQA、16-bit KV 外推。核心结果来自 trace replay，不是线上 A/B。

Editorial Assessment

Why It Matters

它为 LMCache、Mooncake、vLLM/SGLang connector 与 session-aware routing 提供了真实 workload 约束：KV 管理需要跨请求生命周期，而非只做单请求分页。

Limitations

生产模型和原始 traces 不公开；容量基于代理布局估算，外推到其他注意力结构有偏差。AgenticTraceSim 与 replay framework 尚是“计划发布”，当前复现性有限。

Editor Note

93/S。新颖性和产业证据极强；因数据私有、代码尚未发布以及容量估算依赖代理模型扣分。

Abstract

Original Abstract Summary

The work extends Google Cloud Dataflow for hybrid streaming and machine-learning pipelines. It embeds high-performance inference engines, introduces resource hints and heterogeneous worker pools, groups requests for prefix locality, and replaces CPU-centric autoscaling signals with completion-rate-aware capacity estimates.

中文摘要

论文把“在线推理服务”纳入流式处理语义，而不是外挂一个独立集群。Dataflow 仍提供 exactly-once、windowing 与容错，同时让 GPU 推理拥有独立 worker pool、缓存局部性和能理解动态 batching 的扩缩容控制。

Technical Analysis

Problem

传统 streaming engine 为数据搬运与 CPU transform 设计，GPU 推理的长任务、VRAM、dynamic batching 与 prefix locality 会破坏其调度和扩缩容假设。

Method

新增 RunInference、资源提示、异步处理、嵌入式 vLLM/Triton、按 key 的 prefix-aware batching，以及基于完成率和并发分布的 co-designed autoscaler。

Architecture

流式 DAG 按资源提示分成 CPU 与 accelerator worker pools；inference transform 内嵌 engine，worker 汇报请求完成率；控制面结合 active/dispatchable keys 与每 worker capacity 分别扩缩容。

Key Innovation

把流处理的 exactly-once/windowing 与现代 LLM serving 的 cache locality、dynamic batching、异构扩缩容放进同一控制面。

Experiments

Google Cloud Dataflow 上比较优化基线与 Flink；LLM 示例使用 Gemma 4 与 vLLM，硬件包括 T4 等资源池。摘要给出总体最大值，具体 workload 需逐表读取。

Editorial Assessment

Why It Matters

大量企业推理发生在实时 ETL/内容流中；减少独立 serving cluster 与物化中间数据可以显著降低运维和资源浪费。

Limitations

实现依赖 Google Cloud Dataflow，代码与部署可得性有限；prefix-aware 分组依赖用户 key，热点 sharding 会牺牲 cache hit。最大资源/尾延迟数字不是所有 workload 的保证。

Editor Note

88/A+。系统整合和实测有价值，Google 生产栈证据强；闭源依赖和复现门槛限制得分。

Abstract

Original Abstract Summary

The study uses token-, layer- and attention-path interventions across four MoE families to localize the quality loss caused by reducing routed experts during prefill. It finds that a small number of task-interface tokens account for much of the damage and tests selective full-expert rules.

中文摘要

这是一篇“边界条件”研究：少专家 prefill 并非对所有 token 同样安全。答案边界、系统指令等接口位置对短答形式尤其敏感；只保留这些位置的完整专家计算，比随机保留同等预算更有效。

Technical Analysis

Problem

减少 prefill routed experts 可以省算力，但已有工作缺少损失发生位置与机制证据，容易用平均质量掩盖特定 prompt 结构的退化。

Method

对四类 MoE 做 token/layer/attention-path 干预，比较 super expert、activation restoration、敏感位置保留与随机位置保留，并预先规定部分主比较。

Architecture

不改变模型结构；在 serving prefill 路径按 token 选择完整或缩减 expert top-k，decode 保持原配置；策略可由 prompt interface marks 或首尾位置触发。

Key Innovation

把“是否能减专家”转化为“哪些 token 不能减”，并用因果式干预与负控定位答案边界，而非只做端到端 benchmark。

Experiments

四个 MoE 家族、短答 QA 与长 prompt；Qwen3‑30B‑A3B、DeepSeek‑V2‑Lite 等。算力占比与 TTFT 结果受长度、engine 实现影响，作者明确报告 2K 无稳定加速。

Editorial Assessment

Why It Matters

对 MoE serving scheduler，它给出可执行的 selective policy，并提醒优化者不能仅按 token 数或 layer 平均裁剪专家。

Limitations

单作者、短答任务为主；五个预设主比较只有两个完成或显著，且接口 marks 与序列端点尚未完全区分。未提供通用 production scheduler。

Editor Note

84/A。机制证据透明且披露负结果；泛化范围、团队/复现生态和端到端实现有限。

Abstract

Original Abstract Summary

DominoTree combines a block-diffusion drafter with Domino’s path-dependent causal correction and a training-free best-first tree. Version 4 adds fused tree construction, single-GPU serving reruns, tuned budgets and experiments on a hybrid recurrent model, while reporting concurrency and long-context failure boundaries.

中文摘要

方法让树上每条分支都继承 Domino 的条件校正，而不是把各位置视为独立分布。v4 的价值在于从研究 harness 走向单 GPU SGLang 实测，并承认树验证在并发饱和时可能不如简单链式 draft。

Technical Analysis

Problem

并行 block drafter 成本低但忽略分支历史；因果校正 chain 有条件性但无法一次验证多个候选。直接套用普通 tree drafting 会丢失校正。

Method

用 best-first 搜索按 path-dependent score 扩展 top-M 候选，复用路径无关 backbone state 并维护分支 GRU correction；以 fused tree-builder kernel 降低主机/小算子开销。

Architecture

DFlash/类 block backbone 先生成位置状态；Domino recurrent correction 沿每条分支更新；tree builder 选择预算内候选；target model 在 SGLang 中一次 tree-aware verify 并提交接受前缀。混合 recurrent target 需要专门状态验证。

Key Innovation

在不重新训练 drafter 的前提下把部分条件分布嵌入树草拟，并在 v4 补齐 fused kernel 与真实 serving 并发边界。

Experiments

Qwen3‑4B/8B 使用 RTX 5090 单卡 serving；研究 harness 还用 RTX 5080/NCHC；Qwen3.6‑27B 使用 H200。覆盖 8 个数据集、温度、并发与 8K–32K context。

Editorial Assessment

Why It Matters

投机解码论文常只报 batch 1 接受长度；v4 同时给出 kernel、真实 engine、并发反转和长上下文退化，更利于判断部署条件。

Limitations

收益依赖 tree budget、GPU、context 与并发；并发 8+ goodput 可能落后 chain，32K 接受率下降。作者使用生成式 AI 辅助代码/文稿，但声明已审查并开放原始记录。

Abstract

Original Abstract Summary

BaGuaLu-2 addresses dynamic activation-memory spikes caused by imbalanced expert routing in fine-grained MoE training. It models per-batch activation demand, provisions mitigation on demand and amortizes the management overhead with fused dual-batch execution, demonstrating trillion-parameter training across 12,288 GPUs.

中文摘要

系统的核心是让 activation memory provisioning 变成运行时控制问题：正常 batch 不为极端 routing 峰值永久预留空间；高压 batch 才触发精确的 recompute/offload 等缓解动作，并用双 batch 融合隐藏额外开销。

Technical Analysis

Problem

静态显存预算要么为少数 load spike 过度预留、压低 MFU，要么在峰值 OOM 并触发昂贵回滚，尤其在细粒度 MoE 与万卡规模下更严重。

Method

建立 activation cost 与 mitigation cost 模型，逐 batch 预测需求并选择动态缓解方案；通过 fused dual-batch execution 与系统优化摊薄重算/迁移带来的泡泡。

Architecture

训练 runtime 监控 routing-induced activation pressure；模型层计算批次需求和可选缓解代价；执行层在内存安全边界内协调 batch、recompute/offload 与 fused dual-batch，并与现有并行训练栈协作。

Key Innovation

将 MoE 显存波动从离线安全余量转为连续、细粒度控制，并给出 1.04T/12,288 GPU 的大规模验证。

Experiments

端到端对照 Megatron‑Kuai、AdaPipe；最大规模为 1.04T 参数、12,288 GPUs。论文同时报告多种 memory pressure 和 ablation；公开摘要未披露 GPU 型号，HTML 正文需结合表格解读。

Editorial Assessment

Why It Matters

训练成本常由稀有峰值而非平均负载决定。动态 provisioning 能提高 MFU、减少 OOM/人工回滚，并可能成为大规模 MoE runtime 的通用控制面。

Limitations

代码开放状态未披露；硬件与生产环境细节有限，外部团队难以复现万卡结果。与不同 EP/PP/ZeRO 组合的通用性仍需独立验证。

Editor Note

94/S。规模、技术重要性与证据非常强；缺少代码和完整硬件可复现性使其未达 S+。
